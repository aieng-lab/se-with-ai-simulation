\section{Model Description}
\label{sec:model}
% ============================================================

The model treats software development as a discrete-time stochastic dynamical
system. The simulation runs for $T$ sprints; each sprint represents one
fixed-duration iteration. States are indexed $t \in \{0, 1, \ldots, T\}$,
where $S(0)$ is the fixed initial state (before any sprint executes) and
$S(t)$ for $t \geq 1$ is the state produced by sprint $t$. The simulation
horizon is $T$. The simulation configuration is defined by the team composition and process parameters 
$\mathbf{c} = (N, M, \mathbf{A}_\mathrm{dev}, \mathbf{A}_\mathrm{qa}, R, F_\mathrm{freeze})$. The parameters
$N$, $M$, $\mathbf{A}_\mathrm{dev}$, $\mathbf{A}_\mathrm{qa}$ define the team structure (Section~\ref{sec:model:roles}). The parameters $R$ and $F_\mathrm{freeze}$ define the release cycle and feature freezes (Section~\ref{sec:model:cycle}). The team composition further depends on whether the current sprint is in the development phase or the feature freeze phase of the release cycle (Section~\ref{sec:model:team}). The development team of humans and agents evolves a software project whose state at sprint $t$ is represented by a 21-dimensional state vector $S(t)$ defined in Section~\ref{sec:model:state}. Scenario parameters govern the behavior of the underlying software development process and the capabilities of the agents, such as feature throughput rates, bug injection rates, bug detection probabilities, and cost coefficients (Section~\ref{sec:model:parameters}). The transition from $S(t-1)$ to $S(t)$ is governed by the sprint dynamics $\mathcal{T}$, which consists of ten ordered steps (Section~\ref{sec:model:transition}).

We can derive metrics that describe the utility of a team configuration using three objectives (Section~\ref{sec:model:objectives}): the $value$ as the average number of features completed per sprint, the $quality$ as the average number of escaped bugs per completed feature, and the $cost$ as the average cost incurred per completed feature. By exploring different team and process configurations $\mathbf{c}$, we get a multi-objective search problem with the goal to identify optimal configurations with different trade-offs between the objectives (Section~\ref{sec:model:mosp}). By running multiple simulations with different random seeds for each configuration $\mathbf{c}$, we can establish the uncertainty of the simulation through a Monte Carlo approach and estimate the confidence intervals of the objectives (Section~\ref{sec:model:mc}). The outcomes for different configurations form a Pareto frontier that characterises the trade-offs between the objectives and provides practical guidance on how to compose mixed AI-human teams for software development (Section~\ref{sec:model:pareto}). Since the search space is combinatorial and high-dimensional, we further describe different search strategies to efficiently explore the space of valid configurations (Section~\ref{sec:model:search}).

\subsection{Roles}
\label{sec:model:roles}



There is only a single human role included in the model: the \textit{Human
Developer}. Each of the $N$ developers communicates with the other developers, supervises at most $M$ agents,
reviews and approves architecture proposals, resolves
escalations that agents cannot handle autonomously, and contributes new
features and bug fixes with the remaining time. Their total available time is constrained at
$H_\mathrm{capacity}$ hours per sprint. 

We have eight specialist AI agent roles, indexed $k = 1,\ldots,8$. All agents of the
same type are assumed to be statistically identical. Each agent consumes supervision budget from
a human developer but is otherwise assumed to execute tasks autonomously. Table~\ref{tab:roles} summarises each AI agent role's primary function.

The eight roles fall into three functional groups. The production roles
(k = 1,\ldots,4) all directly contribute to the production code. 
The \textit{Feature Implementation Agent} is the primary
productivity driver implementing features and architecture changes. While doing so, the agent also generates
architecture change requests and introduces new bugs into the codebase.
The \textit{Architecture Agent} creates proposals for architecture updates for human review. Neglecting architecture change requests degrades internal quality and will lead to architectural debt accumulation.
The \textit{Bug Fixing Agent} drains the known-bug
queue. The work conducted by the Feature Implementation and Bug Fixing Agents introduces technical debt.
The \textit{Refactoring Agent} improves the internal quality of the system autonomously and reduces technical debt.
From a conceptual perspective, the \textit{Architecture Agent} is responsible for high-stakes structural changes that require human review, while the \textit{Refactoring Agent} is responsible for low-stakes internal improvements that can be executed autonomously without review. 

The detection roles (k = 5,\ldots,7) inspect
every code change synchronously in the same sprint as injection. The \textit{Code Review
Agent} detects all kinds of defects but gets less effective if there is more code to review. The \textit{Security Audit Agent} can only detect security defects and allows the modeling of more expensive agents for this high-stakes role. The \textit{Test Development Agent} builds up a continuously growing test suite, which helps detect bugs.

Finally, there is one \emph{support role} (k = 8): the \textit{Developer Documentation Agent} creates documentation to aid human developers, which in turn reduces the
per-agent monitoring overhead that consumes human capacity by reducing the cognitive load
of the human developers when supervising agents.

\subsection{Release Cycle and Feature Freezes}
\label{sec:model:cycle}

A release occurs exactly at sprint indices $R, 2R, 3R, \ldots$ where $R \geq 1$
is the fixed release cadence. At each release, unfixed bugs (both hidden and known)
escape to production, incrementing the cumulative escaped bug counters. 
Similar to real-world projects, a feature freeze is implemented to stabilise the
codebase before release. The feature freeze lasts for $F_\mathrm{freeze} \in
[0, R-1]$ sprints before a release.
Sprint $t$ is in the freeze window iff $((t-1) \bmod R) \geq R - F_\mathrm{freeze}$, i.e., the freeze window comprises the last $F_\mathrm{freeze}$ sprints of each release cycle, including the release sprint itself.

Each sprint selects the active agent composition based on its
position in the release cycle: the \emph{development composition}
is used during the first $R - F_\mathrm{freeze}$
sprints of each cycle; the \emph{QA composition} is
used during the remaining $F_\mathrm{freeze}$ sprints. The different compositions allow a different focus,
i.e., focus on feature addition versus focus on quality assurance and bug fixing.

\subsection{Project and team structure}
\label{sec:model:team}

Given the above description of the roles and release cycle, we can now specify the project and team structure using six control variables: the human developer count
$N \geq 1$, the number of agents each developer can control at most $M \geq 1$, the number of sprints per release $R \geq 1$, the length of the feature freeze period $F_\mathrm{freeze} \in
[0, R-1]$, and two 8-element agent composition vectors $\mathbf{A}_\mathrm{dev}$ and
$\mathbf{A}_\mathrm{qa}$ described below.

$\mathbf{A}_\mathrm{dev} = (a_{dev,1},\ldots,a_{dev,8}) \in \mathbb{N}_{\geq 0}^{8}$ is the
development-phase composition and $\mathbf{A}_\mathrm{qa} = (a_{qa,1},\ldots,a_{qa,8}) \in \mathbb{N}_{\geq 0}^{8}$ is the QA composition. Both vectors satisfy the same \emph{budget constraint}
\begin{equation}
  n(t) = \sum_{k=1}^{8} a_{\cdot,k} \leq N \cdot M,
  \label{eq:budget}
\end{equation}
i.e., the number of active agents is bounded by the supervision capacity of the human developers.
The inequality allows for the possibility of leaving some agent slots unfilled, which may be optimal in some cases to reduce coordination overhead and free up human capacity for review, escalation, and implementation work. 
$\mathbf{A}_\mathrm{dev}$ must satisfy $a_{dev,1} \geq 1$, i.e., there must be at least one Feature
Implementation Agent in the development phase. This also ensures that there is $value$, i.e., that at least some features are implemented and the simulation does not trivially collapse to zero throughput.
For $F_\mathrm{freeze} \geq 1$, $\mathbf{A}_\mathrm{qa}$ is required to have $a_{qa,1} = a_{qa,2} = 0$, to ensure that no new features are added during a feature freeze and that all agents are redeployed to QA roles. If $F_\mathrm{freeze}=0$, the QA composition is never active and has no effect on the simulation.

\subsection{State Space}
\label{sec:model:state}

$S(t)$ denotes the 21-component system state produced by sprint $t$ (for $t \geq 1$); $S(0)$ is the fixed initial state. The components fall into four
clusters summarised in Table~\ref{tab:state}: two variables that describe the features in the backlog and completed; twelve variables that track bugs in their various stages; five variables that track technical debt and human capacity queues; and two variables that track test infrastructure and documentation coverage.

\subsubsection{Feature pipeline}
$F_\mathrm{backlog}(t) \in \mathbb{N}_{\geq 0}$ counts features awaiting
implementation after sprint $t$ completed. Within each sprint, this queue grows governed by the configuration parameters (see Section~\ref{sec:model:parameters}), while the \textit{Feature Implementation Agents} and the
direct coding capacity of \textit{Human Developers} reduce the value of pending features by implementing them and thereby growing the monotonically increasing cumulative count of fully implemented features $F_\mathrm{completed}(t) \in \mathbb{N}_{\geq 0}$.

\subsubsection{Bug queues}

Our simulation model distinguishes between three mutually exclusive bug types: \emph{minor}, \emph{major}, and \emph{security} bugs. Configuration parameters determine the impact of the different bug types on quality and the rates at which bugs of the different types are introduced, relative to each other (see Section~\ref{sec:model:parameters}). The bugs are tracked at four queue kinds — hidden, known, released, and escaped — and each
kind maintains one counter per type, giving twelve bug state variables in total.

$B_\mathrm{hid,x}(t)$ (for $x \in \{\mathrm{min, maj, sec}\}$) counts type-$x$ bugs
that have been injected in the current release cycle but not been detected yet.
$B_\mathrm{kno,x}(t)$ counts type-$x$ bugs that have been detected and are queued for
repair. The separation between hidden and known is load-bearing: fixing capacity is
consumed only by detected bugs, while hidden bugs silently degrade quality. $B_\mathrm{esc,x}(t) \in \mathbb{N}_{\geq 0}$ is the
monotonically increasing cumulative count of type-$x$ bugs that reached production.
Since escaped bugs must still be fixed, $B_\mathrm{rel,x}(t)$ counts the subset of
escaped type-$x$ bugs still open at the start of sprint $t$; these are served with
priority by the Bug Fixing Agent ahead of the known-bug queue.

\subsubsection{Technical debt and human capacity queues.}

$D_\mathrm{tech}(t) \in [0, 1]$ is a normalised measure of technical debt: $D_\mathrm{tech} = 0$ represents
a debt-free codebase and $D_\mathrm{tech} = 1$ represents maximum degradation. $D_\mathrm{tech}(t)$ can be reduced autonomously by the \textit{Refactoring Agent}. $Q_\mathrm{arch}(t) \in \mathbb{N}_{\geq 0}$ counts the architecture change requests that are still pending, $Q_\mathrm{rev}(t) \in \mathbb{N}_{\geq 0}$ counts the architecture proposals awaiting human review, and $Q_\mathrm{arch,impl}(t) \in \mathbb{N}_{\geq 0}$ counts the approved architecture proposals that are awaiting implementation. Together, these three variables measure the architectural degradation, which requires human intervention to be reduced and cannot be reduced fully autonomously. $Q_\mathrm{esc}$ is the agent escalation queue: agents may fail to implement a feature on their own and need to escalate this to a human developer to resolve the issue. 

All these variables grow with the work of the Feature Implementation Agents and the Bug Fixing Agents, which introduce technical debt and generate architecture change requests as they implement features and fix bugs. Thus, faster development speed directly increases the accumulation of technical debt, architectural debt, and escalation requests.

\subsubsection{Test infrastructure and documentation.}

We assume that there is a continuous integration system in place that automatically runs a test suite to detect
bugs. The status of this test suite is tracked by $N_\mathrm{test}(t)$, which is the cumulative number of tests written by the Test
Development Agent. New tests are added every sprint to increase the \emph{test coverage} $\mathrm{cov\_test}$, which is derived from the test count and the number of implemented features as
\begin{equation}
  \mathrm{cov\_test}(t) = \min\!\left(c_\mathrm{test,ceil},\;
    \frac{N_\mathrm{test}(t)}{\max\!\bigl(1,\,F_\mathrm{completed}(t)\bigr)}\right),
  \label{eq:coverage}
\end{equation}
Higher coverage increases the likelihood that introduced defects are detected to move bugs from the hidden to the known queues. 

Similarly, $N_\mathrm{doc}(t)$ is the cumulative number of documentation items produced by
the Developer Documentation Agent and grows monotonically each sprint.
Documentation \emph{coverage} is derived from this count relative to
$F_\mathrm{completed}(t-1)$ in the same way as test coverage:
\begin{equation}
  \mathrm{doc\_cov}(t-1) = \min\!\left(1,\;
    \frac{N_\mathrm{doc}(t-1)}{\max\!\bigl(1,\,F_\mathrm{completed}(t-1)\bigr)}\right),
  \label{eq:doc_cov}
\end{equation}
capped at 1, i.e.\ full documentation coverage.
The $t-1$ index reflects that the documentation is updated at the end of the sprint, i.e., the new documentation only becomes available in the next sprint. This means that the benefits of documentation investment (i.e., reduced monitoring effort for human developers) are always lagged by one sprint.

\subsection{Configuration Parameters}
\label{sec:model:parameters}

The behavior of the agents and the simulation model in each sprint
is governed by a set of parameters that must be defined before running the simulation. 
The parameters codify the assumptions about the underlying software development process and the capabilities of the agents, and they determine how the state variables evolve over time. They can be grouped into human-capacity parameters (Table~\ref{tab:params:human}), feature-pipeline and throughput-rate parameters (Table~\ref{tab:params:pipeline}), bug-injection parameters (Table~\ref{tab:params:injection}), quality assurance parameters for bug detection (Table~\ref{tab:params:detection}), technical-debt parameters (Table~\ref{tab:params:debt}), and cost parameters (Table~\ref{tab:params:costs}). The tables describe the meaning of each parameter, its domain, and which step of the sprint transition first uses it (see Section~\ref{sec:model:transition} for the step definitions). How exactly each of the parameters is used is described in Section~\ref{sec:model:transition}; how we initialize them will be discussed as part of the experiments (see Section~\ref{sec:setup}).

\subsection{Sprint Transition Function}
\label{sec:model:transition}

The sprint transition $\mathcal{T}: S(t-1) \to S(t)$ executes ten steps in
fixed dependency order. 

% TODO: Figure 3 -- data-flow diagram of the 10-step transition

\subsubsection*{Step 1 --- Human Capacity Allocation}
\label{sec:transition:prelim}

The priority-ordered time budget of the developers is
resolved as a five-stage cascade, each stage consuming time that is remaining from the previous stage.
First, communication overhead between the developers reduces capacity to
$H_\mathrm{net} = H_\mathrm{capacity} - c_\mathrm{comm}(N-1)$
per developer. Since $n(t)$ is the total number of active agents, each developer supervises
$\frac{n(t)}{N}$ agents, consuming $\frac{n(t)}{N} \cdot H_\mathrm{mon,eff}(t)$ hours of monitoring effort. The per-agent monitoring effort is reduced by the documentation coverage $\mathrm{doc\_cov}(t-1)$ (from the previous sprint) and the reduction is calibrated by $\Gamma_\mathrm{doc}$
\begin{equation}
  H_\mathrm{mon,eff}(t) = H_\mathrm{mon.overhead}\,
    \bigl(1 - \Gamma_\mathrm{doc}\,\mathrm{doc\_cov}(t-1)\bigr),
  \label{eq:hmoneff}
\end{equation}
leaving post-monitoring capacity
\begin{equation}
  H_\mathrm{after\_mon}(t) = H_\mathrm{net} -
    \frac{n(t)}{N}\,H_\mathrm{mon,eff}(t).
  \label{eq:hafter_mon}
\end{equation}
We assume $\Gamma_\mathrm{doc} \leq 1$, so that documentation reduces, but never inverts, the monitoring effort.

Architecture reviews are served from this remainder and drain the architecture review queue $Q_\mathrm{rev}(t-1)$ at rate
$N/H_\mathrm{review\_time}$:
\begin{align}
  \mathrm{rev\_done}(t) &= \min\!\Bigl(
    \bigl\lfloor H_\mathrm{after\_mon}(t)\cdot N\,/\,H_\mathrm{review\_time}\bigr\rfloor,\;
    Q_\mathrm{rev}(t-1)\Bigr),
  \label{eq:rev_done}
\end{align}
leaving post-review capacity
\begin{equation}
  H_\mathrm{after\_rev}(t) =
    H_\mathrm{after\_mon}(t) - \mathrm{rev\_done}(t)\,H_\mathrm{review\_time}/N.
  \label{eq:hafter_rev}
\end{equation}
Escalations are served analogously:
\begin{equation}
  \mathrm{esc\_done}(t) = \min\!\Bigl(
    \bigl\lfloor H_\mathrm{after\_rev}(t)\cdot N\,/\,H_\mathrm{esc\_time}\bigr\rfloor,\;
    Q_\mathrm{esc}(t-1)\Bigr),
  \label{eq:esc_done}
\end{equation}
leaving post-escalation capacity
\begin{equation}
  H_\mathrm{after\_esc}(t) =
    H_\mathrm{after\_rev}(t) - \mathrm{esc\_done}(t)\,H_\mathrm{esc\_time}/N.
  \label{eq:hafter_esc}
\end{equation}
The remaining capacity $H_\mathrm{after\_esc}(t)$ is used for coding:
fraction $f_\mathrm{fix}$ goes to bug fixing and $(1-f_\mathrm{fix})$ to feature implementation:
\begin{align}
  \mathrm{fix\_human}(t)  &=
    \bigl\lfloor N\,f_\mathrm{fix}\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{fix}\bigr\rfloor,
  \label{eq:fixhuman} \\
  \mathrm{impl\_human}(t) &=
    \bigl\lfloor N\,(1-f_\mathrm{fix})\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{feature}\bigr\rfloor.
  \label{eq:implhuman}
\end{align}
During feature-freeze sprints (Section~\ref{sec:model:cycle}), $\mathrm{impl\_human}=0$ and
all of $H_\mathrm{after\_esc}(t)$ is redirected to bug fixing:
\begin{equation}
  \mathrm{fix\_human}(t)\big|_\mathrm{freeze} =
    \bigl\lfloor N\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{fix}\bigr\rfloor.
  \label{eq:fixhuman_freeze}
\end{equation}
Both activities are debt-independent: $h_\mathrm{feature}$ and $h_\mathrm{fix}$ are fixed
costs regardless of the current debt level $D_\mathrm{tech}(t-1)$. While not fully realistic, this assumption simplifies the model and assumes that human effort includes dealing with possibly existing debt-related complexity. 

$H_\mathrm{after\_mon}(t)$ can be negative if monitoring overhead exceeds $H_\mathrm{net}$.
Configurations for which this is unavoidable cannot perform any productive human work regardless of the scenario-parameter draws. We therefore define a feasibility criterion that is checked for the development composition $\mathbf{A}_\mathrm{dev}$ before running the simulation:
\begin{align}
  H_\mathrm{net} = H_\mathrm{capacity} - c_\mathrm{comm}(N-1) &\geq 0 \\
  \frac{\sum_{k=1}^{8} a_{\mathrm{dev},k}}{N}\,H_\mathrm{mon.overhead}\,
    (1 - \Gamma_\mathrm{doc}) &< H_\mathrm{net}.
  \label{eq:feas_monitoring}
\end{align}
This check ensures that the developers have sufficient capacity for the communication between
themselves and for the monitoring of agents under the best-case assumption of perfect documentation coverage. The criterion is a necessary condition rather than a sufficient one: since the documentation coverage starts below its ceiling, the effective monitoring overhead early in a simulation run can still temporarily exceed the available capacity. We do not specify similar constraints for architecture review and escalation time, as not handling these only increases the debt penalties we discuss next, meaning that implementation is still possible, though less efficient.

\subsubsection*{Step 2 --- Debt Penalties}

Technical debt $D_\mathrm{tech}$, as well as unresolved work in the architecture
and escalation pipelines contribute to productivity degradation.
Architecture work is considered unresolved as long as it remains anywhere in
the pipeline: as an unprocessed change request ($Q_\mathrm{arch}$), as a design
proposal awaiting human review ($Q_\mathrm{rev}$), or as an approved proposal
awaiting implementation ($Q_\mathrm{arch,impl}$). We normalize this by the team's \emph{maximum throughput} for the
corresponding human activity in one sprint
$H_\mathrm{capacity} \cdot N \;/\; H_{x}$.
A value of~1 means the queue holds as many items as the team could process in
an entire sprint under ideal conditions, i.e., the team would need a full sprint just to drain the queue. Once the queue reaches this or a worse state, the architectural degradation has reached its maximum. Step~2 reads queue values carried over from sprint $t-1$, so all debt quantities use the $t-1$ index. Overall, this gives us the architectural debt as
\begin{equation}
  D_\mathrm{arch}(t-1) = \min\!\Bigl(1,\;
    \frac{Q_\mathrm{arch}(t-1) + Q_\mathrm{rev}(t-1) + Q_\mathrm{arch,impl}(t-1)}
         {H_\mathrm{capacity}\,N \;/\; H_\mathrm{review\_time}}\Bigr).
  \label{eq:D_arch}
\end{equation}
A long escalation queue likewise signals a team under strain: unresolved
escalations indicate that agents require frequent human intervention, which
degrades coordination quality.  Normalising by the maximum escalation throughput
$H_\mathrm{capacity}\,N / H_\mathrm{esc\_time}$ gives
\begin{equation}
  D_\mathrm{esc}(t-1) = \min\!\Bigl(1,\;
    \frac{Q_\mathrm{esc}(t-1)}
         {H_\mathrm{capacity}\,N \;/\; H_\mathrm{esc\_time}}\Bigr).
  \label{eq:D_esc}
\end{equation}
The combined effective debt is
\begin{equation}
  D_\mathrm{eff}(t-1) = \min\!\bigl(1,\; D_\mathrm{tech}(t-1) + D_\mathrm{arch}(t-1) + D_\mathrm{esc}(t-1)\bigr).
  \label{eq:D_eff}
\end{equation}
The \emph{debt amplifier}
\begin{equation}
  \delta_D = 1 - (1 - \delta_\mathrm{min})\,D_\mathrm{eff}(t-1)^{\delta_\mathrm{exp}}
  \label{eq:delta_D}
\end{equation}
is a single function of the combined debt, parameterised by a floor
$\delta_\mathrm{min} \in (0,1)$ that describes the highest negative impact the debt can have and shape exponent $\delta_\mathrm{exp} > 0$ that controls the rate of decay.
It equals~1 at zero combined debt and decays to $\delta_\mathrm{min}$ at
$D_\mathrm{eff} = 1$. This debt multiplier will be used in subsequent steps to reduce feature implementation speed, increase bug injection, reduce code review quality, and increase the rate at which agents require escalations. 

\subsubsection*{Step 3 --- Feature Arrival and Implementation}
In every sprint, new features arrive to the backlog according to
\begin{equation}
  \mathrm{arrivals}(t) \sim \mathrm{Poisson}(r_\mathrm{arrival}),
  \label{eq:arrivals}
\end{equation}
growing the backlog at the beginning of the step. Because arrivals are added before implementation runs, newly arrived features are immediately available for implementation in the same sprint. The backlog is then drained by human and agent implementation.

Available agent capacity is first consumed by approved architecture proposals
$Q_\mathrm{arch,impl}(t-1)$ pending implementation, with remaining capacity applied
to the feature backlog:
\begin{align}
  \mathrm{arch\_impl}(t) &= \min\!\Bigl(Q_\mathrm{arch,impl}(t-1),\;
    \bigl\lfloor r_F\,\delta_D\,a_1\bigr\rfloor\Bigr),
  \label{eq:arch_impl} \\
  \mathrm{impl\_agents}(t) &= \min\!\Bigl(F_\mathrm{backlog}(t-1) + \mathrm{arrivals}(t),\;
    \bigl\lfloor r_F\,\delta_D\,a_1\bigr\rfloor - \mathrm{arch\_impl}(t)\Bigr).
  \label{eq:impl_agents}
\end{align}
Implementing approved architecture proposals ($\mathrm{arch\_impl}$) consumes agent
capacity but does not increment $F_\mathrm{completed}$, since it represents internal
architecture work rather than user-visible feature delivery. The feature implementation is linearly reduced by $\delta_D$ to reflect the impact of debt on development speed.
Total user-feature implementation per sprint is capped at the available backlog to
prevent over-counting features:
\begin{equation}
  \mathrm{impl}(t) = \min\!\bigl(\mathrm{impl\_agents}(t) + \mathrm{impl\_human}(t),\;
    F_\mathrm{backlog}(t-1) + \mathrm{arrivals}(t)\bigr),
  \label{eq:impl}
\end{equation}
and the state variables are updated as:
\begin{align}
  F_\mathrm{backlog}(t)   &= F_\mathrm{backlog}(t-1) + \mathrm{arrivals}(t) - \mathrm{impl}(t),
    \label{eq:backlog_update} \\
  F_\mathrm{completed}(t) &= F_\mathrm{completed}(t-1) + \mathrm{impl}(t).
    \label{eq:completed_update}
\end{align}

\subsubsection*{Step 4 --- Test Suite Update}
The Test Development Agent grows the
cumulative test count before bug detection runs:
\begin{equation}
  N_\mathrm{test}(t) = N_\mathrm{test}(t-1) + r_\mathrm{test}\,a_7.
  \label{eq:ntest_update}
\end{equation}
Because this step executes before bug injection and detection (Step~5), the new
tests written this sprint are immediately available to raise the test coverage
$\mathrm{cov\_test}$. Investment in testing therefore
pays off in the sprint it occurs, creating a direct incentive to allocate
agents to the Test Development role.

\subsubsection*{Step 5 --- Bug Injection and Detection}
Each implemented feature injects defects at an effective per-feature rate
\begin{equation}
  r_\mathrm{bugs,eff}(t) = r_\mathrm{bugs}\,(2 - \delta_D),
  \label{eq:r_bugs_eff}
\end{equation}
where the factor $(2 - \delta_D) \in [1,\, 2 - \delta_\mathrm{min}]$ increases the bug injection as debt accumulates.
Bugs are drawn in two independent Poisson streams -- one for
agent-implemented features and one for human-implemented features -- and
then summed:
\begin{align}
  B_\mathrm{agents}(t) &\sim
    \mathrm{Poisson}\!\bigl(\mathrm{impl\_agents}(t)\cdot r_\mathrm{bugs,eff}(t)\bigr),
    \nonumber \\
  B_\mathrm{human}(t)  &\sim
    \mathrm{Poisson}\!\bigl(\mathrm{impl\_human}(t)\cdot r_\mathrm{bugs,eff}(t)
      \cdot r_\mathrm{bugs,human}\bigr),
    \nonumber \\
  B_\mathrm{inj}(t)    &= B_\mathrm{agents}(t) + B_\mathrm{human}(t),
  \label{eq:Binj}
\end{align}
where $r_\mathrm{bugs,human}$ reflects the ratio of defect density of
human-written code relative to agent-generated code.

Each injected bug is assigned to exactly one of three mutually exclusive types via
a sequential draw: security bugs are extracted first, then the remainder is split
into major and minor:
\begin{align}
  B_\mathrm{sec}(t) &\sim \mathrm{Binomial}\!\bigl(B_\mathrm{inj}(t),\;\theta_\mathrm{sec}\bigr),
    \nonumber \\
  B_\mathrm{maj}(t) &\sim \mathrm{Binomial}\!\Bigl(B_\mathrm{inj}(t)-B_\mathrm{sec}(t),\;
    \tfrac{\theta_\mathrm{maj}}{\theta_\mathrm{min}+\theta_\mathrm{maj}}\Bigr),
    \nonumber \\
  B_\mathrm{min}(t) &= B_\mathrm{inj}(t) - B_\mathrm{sec}(t) - B_\mathrm{maj}(t),
  \label{eq:type_split}
\end{align}
where $\theta_\mathrm{min} = 1 - \theta_\mathrm{maj} - \theta_\mathrm{sec}$.

Detection proceeds in three sequential stages that model a workflow where first an existing test suite is run against code
changes (simulating a CI pipeline), then code review is conducted, and finally a security audit is performed by a specialist agent. 

The test suite detect bugs at rate
\begin{equation}
  p_\mathrm{test}(t) = \min\!\bigl(1,\; d_\mathrm{test}\,\mathrm{cov\_test}(t)\bigr),
  \label{eq:p_test}
\end{equation}
where $\mathrm{cov\_test}(t)$ is given by Eq.~\eqref{eq:coverage}. The code review
then detects bugs that survive testing at effective rate
\begin{equation}
  d_\mathrm{CR,eff}(t) = \min\!\Bigl(1,\; d_\mathrm{CR}\,\delta_D\,
    \max\!\Bigl(0,\; 1 - \alpha_\mathrm{size}
      \log\!\bigl((\mathrm{impl}(t)+1)\,/\,\mathrm{baseline\_size}\bigr)\Bigr)\Bigr).
  \label{eq:dcr_eff}
\end{equation}
$\alpha_\mathrm{size}$ is the change-volume degradation
slope and $\mathrm{baseline\_size}$ the reference change size; the outer minimum keeps the
detection rate a valid probability for change volumes below $\mathrm{baseline\_size}$. Thus, review effectiveness
degrades with both accumulated debt $\delta_D$ and change volume.
Finally, the Security Audit Agent detects security bugs at fixed rate $d_\mathrm{SA}$.

Let $T_x(t)$, $C_x(t)$ denote the counts detected by tests and code review for type
$x$, and $A_\mathrm{sec}(t)$ the count detected by the security audit. These are given by binomial draws with the corresponding detection probabilities:
\begin{align}
  T_x(t)        &\sim \mathrm{Binomial}\!\bigl(B_x(t),\; p_\mathrm{test}(t)\bigr),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  C_x(t)        &\sim \mathrm{Binomial}\!\bigl(B_x(t)-T_x(t),\; d_\mathrm{CR,eff}(t)\bigr),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  A_\mathrm{sec}(t) &\sim \mathrm{Binomial}\!\bigl(B_\mathrm{sec}(t)-T_\mathrm{sec}(t)-C_\mathrm{sec}(t),\; d_\mathrm{SA}\bigr).
    \nonumber
\end{align}
The known and hidden queues are incremented accordingly:
\begin{align}
  B_\mathrm{kno,x}(t)   &= B_\mathrm{kno,x}(t-1) + T_x(t) + C_x(t),
    & x &\in \{\mathrm{min,maj}\}, \label{eq:bkno_update} \\
  B_\mathrm{kno,sec}(t) &= B_\mathrm{kno,sec}(t-1) + T_\mathrm{sec}(t) + C_\mathrm{sec}(t) + A_\mathrm{sec}(t),
    \nonumber \\
  B_\mathrm{hid,x}(t)   &= B_\mathrm{hid,x}(t-1) + B_x(t) - T_x(t) - C_x(t),
    & x &\in \{\mathrm{min,maj}\}, \nonumber \\
  B_\mathrm{hid,sec}(t) &= B_\mathrm{hid,sec}(t-1) + B_\mathrm{sec}(t) - T_\mathrm{sec}(t) - C_\mathrm{sec}(t) - A_\mathrm{sec}(t).
    \nonumber
\end{align}
Note that $B_\mathrm{kno,x}(t)$ is an intermediate value at this step, which will be decreased by the bug fixing conducted in Step~8. 

\subsubsection*{Step 6 --- Architecture Queues}
This step propagates architecture work through three queues $Q_\mathrm{arch}$, $Q_\mathrm{rev}$, and $Q_\mathrm{arch,impl}$ in causal order. First, we determine how many new architecture change requests are generated by the features implemented this sprint.
Architecture change requests are generated at rate $f_\mathrm{arch,chg}$ per
feature implemented this sprint,
giving Poisson-distributed arrivals that fill the change-request queue:
\begin{align}
  \mathrm{arch\_chg\_new}(t) &\sim \mathrm{Poisson}\!\bigl(f_\mathrm{arch,chg}\cdot\mathrm{impl}(t)\bigr) \\
  Q_\mathrm{arch}(t) &= Q_\mathrm{arch}(t-1) + \mathrm{arch\_chg\_new}(t).
  \label{eq:arch_chg_new}
\end{align}

Then, the Architecture Agents drain $Q_\mathrm{arch}$ at rate $r_\mathrm{arch,chg}$ per agent.
Each resolved change request produces one design proposal forwarded to the human
review queue $Q_\mathrm{rev}$, which is at the same time reduced by the human review capacity:
\begin{align}
  \mathrm{arch\_chg\_done}(t) &= \min\!\bigl(Q_\mathrm{arch}(t),\;
    \lfloor r_\mathrm{arch,chg}\,a_2\rfloor\bigr), \label{eq:arch_chg_done} \\
  Q_\mathrm{arch}(t) &= Q_\mathrm{arch}(t) - \mathrm{arch\_chg\_done}(t),
    \label{eq:Q_arch} \\
  Q_\mathrm{rev}(t) &= \max\!\bigl(0,\;
    Q_\mathrm{rev}(t-1) + \mathrm{arch\_chg\_done}(t) - \mathrm{rev\_done}(t)\bigr).
    \label{eq:Q_rev}
\end{align}

Finally, the $\mathrm{rev\_done}(t)$ proposals reviewed and approved this sprint are placed
into the \emph{architecture implementation queue} $Q_\mathrm{arch,impl}$, enabling their implementation in the next sprint by the Implementation Agents in Step~3:
\begin{equation}
  Q_\mathrm{arch,impl}(t) = \max\!\bigl(0,\;
    Q_\mathrm{arch,impl}(t-1) + \mathrm{rev\_done}(t) - \mathrm{arch\_impl}(t)\bigr).
  \label{eq:Q_arch_impl}
\end{equation}

\subsubsection*{Step 7 --- Escalation Queue}
Each of the $n(t)$ deployed agents raises a human escalation with per-agent rate
$\rho_\mathrm{esc}$, so new arrivals each sprint are
$\mathrm{esc\_new}(t) \sim \mathrm{Poisson}(n(t)\,\rho_\mathrm{esc})$. The queue is then updated taking
the capacity for human escalation resolution $\mathrm{esc\_done}(t)$ into account:
\begin{equation}
  Q_\mathrm{esc}(t) = \max\!\bigl(0,\;
    Q_\mathrm{esc}(t-1) + \mathrm{esc\_new}(t) - \mathrm{esc\_done}(t)\bigr),
  \label{eq:qesc}
\end{equation}

\subsubsection*{Step 8 --- Bug Fixing}
Bug fixing proceeds in two phases using the same six priority tiers
($B_\mathrm{rel,sec} \to B_\mathrm{kno,sec} \to B_\mathrm{rel,maj} \to
B_\mathrm{kno,maj} \to B_\mathrm{rel,min} \to B_\mathrm{kno,min}$):

\emph{Phase 1 — Human fixes (debt-independent):} Human developers apply their
bug-fixing budget $\mathrm{fix\_human}(t)$ to the priority tiers in order. Each bug fixed
consumes one unit of the integer budget, so:
\begin{equation}
  n^H_i(t) = \min\!\Bigl(\text{queue}_i(t),\; B^H_i(t)\Bigr),
  \qquad B^H_{i+1}(t) = B^H_i(t) - n^H_i(t),
  \label{eq:human_fixes}
\end{equation}
where $B^H_1(t) = \mathrm{fix\_human}(t)$.

\emph{Phase 2 — Agent fixes (debt-slowed):} Bug Fixing Agents drain the
remaining queues with a shared work budget
\begin{equation}
  W(t) = a_3\,\delta_D,
  \label{eq:fix_budget}
\end{equation}
measured in agent-sprint units and scaled by the debt amplifier $\delta_D$. Fixing one bug of type $x$ consumes $1/r_\mathrm{fix,x}$
work units:
\begin{align}
  n^A_i(t) &= \min\!\Bigl(\text{queue}_i(t) - n^H_i(t),\;
    \bigl\lfloor W_i(t)\,r_\mathrm{fix,x_i}\bigr\rfloor\Bigr),
  \label{eq:fixes} \\
  W_{i+1}(t) &= W_i(t) - n^A_i(t)\,/\,r_\mathrm{fix,x_i}, \nonumber
\end{align}
where $W_1 = W(t)$ and $x_i$ is the bug type of tier $i$.
Separate rates $r_\mathrm{fix,min} \geq r_\mathrm{fix,maj} \geq r_\mathrm{fix,sec}$
reflect the increasing effort required for major and security defects.
Human fixes are debt-independent and take priority, so a well-staffed team can
shield the known-bug queue from debt effects even when $\delta_D$ is low.

Letting $n_i(t) = n^H_i(t) + n^A_i(t)$ denote the total bugs fixed from tier $i$
across both phases, the release and known-bug queues are decremented:
\begin{align}
  B_\mathrm{rel,sec}(t) &= B_\mathrm{rel,sec}(t-1) - n_1(t), \nonumber \\
  B_\mathrm{kno,sec}(t) &= B_\mathrm{kno,sec}(t)   - n_2(t), \nonumber \\
  B_\mathrm{rel,maj}(t) &= B_\mathrm{rel,maj}(t-1) - n_3(t), \nonumber \\
  B_\mathrm{kno,maj}(t) &= B_\mathrm{kno,maj}(t)   - n_4(t), \nonumber \\
  B_\mathrm{rel,min}(t) &= B_\mathrm{rel,min}(t-1) - n_5(t), \nonumber \\
  B_\mathrm{kno,min}(t) &= B_\mathrm{kno,min}(t)   - n_6(t).
  \label{eq:bfix_update}
\end{align}
The $B_\mathrm{rel,x}$ rows use index $t-1$ on the right because the release
queues are not written by any earlier step in this sprint.  The $B_\mathrm{kno,x}$
rows use index $t$ as a reminder that their right-hand side values
were already updated by Step~5.

\subsubsection*{Step 9 --- General Maintenance}
Subsequent to the feature implementation, testing, and bug fixing steps, the general maintenance
agents perform their work. They do not provide direct utilitarian value in the form of features delivered or bugs fixed, but instead provide indirect value by slowing the accumulation of technical debt and by improving the documentation, which reduces the cognitive load of the human developers when supervising agents.

The first such activity is performed by the Refactoring Agent, which reduces technical debt. 
Three activities drive the technical debt $D_\mathrm{tech}(t)$: feature implementation and
bug fixing each \emph{increase} debt, while refactoring conducted by the Refactoring Agent 
\emph{decreases} it.
\begin{equation}
\begin{split}
  D_\mathrm{tech}(t) = \operatorname{clip}\bigl(D_\mathrm{tech}(t-1)
    &+ \delta_\mathrm{impl}\,\mathrm{impl}(t) \\
    &+ \delta_\mathrm{fix}\,\mathrm{fixes\_total}(t) \\
    &- r_\mathrm{refactor}\,a_4,\; 0,\, 1\bigr),
  \label{eq:debt_update}
\end{split}
\end{equation}
where $\mathrm{fixes\_total}(t) = \sum_{i=1}^{6} n_i(t)$ is the total number of bugs fixed across all priority tiers in Step~8.

The second activity is documentation written by the Developer Documentation Agent which grows the cumulative
document count:
\begin{equation}
  N_\mathrm{doc}(t) = N_\mathrm{doc}(t-1) + r_\mathrm{doc}\,a_8.
  \label{eq:ndoc_update}
\end{equation}
This increases the documentation coverage $\mathrm{doc\_cov}$ in the next
sprint (see Eq.~\eqref{eq:doc_cov}).

\subsubsection*{Step 10 --- Release Event}
If $t \bmod R = 0$, a release fires: all bugs remaining in the hidden and known queues
escape to production: bugs that were never detected as well as bugs that were detected but not fixed before the release deadline.
These bugs are added to the cumulative escaped counter
and to the in-production repair queue. Afterwards, the hidden and known queues are reset to zero:
\begin{align}
  B_\mathrm{esc,x}(t)  &= B_\mathrm{esc,x}(t-1) + B_\mathrm{hid,x}(t) + B_\mathrm{kno,x}(t),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{rel,x}(t)  &= B_\mathrm{rel,x}(t)   + B_\mathrm{hid,x}(t) + B_\mathrm{kno,x}(t),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{hid,x}(t)  &= 0,
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{kno,x}(t)  &= 0,
    & x &\in \{\mathrm{min,maj,sec}\}.
  \label{eq:release_update}
\end{align}
The $B_\mathrm{rel,x}$ rows use the unindexed $t$ form on the right because the
release queue was already updated by Step~8 (bug fixing) within this sprint;
similarly $B_\mathrm{kno,x}(t)$ on the right is the post-fixing value from
Steps~5 and~8. When $t \bmod R \neq 0$ no release fires and all updates are skipped.

% ---- 3.7 ----
\subsection{Objective Functions}
\label{sec:model:objectives}

The model is designed to evaluate the Pareto trade-offs between three key objectives: value, quality, and costs. These objectives are computed at the end of the $T$-sprint simulation horizon and effectively aggregate performance across the entire development cycle. The main criteria are the value approximated by the number of features that were developed, the quality approximated by the number of bugs that escaped to production, and the total cost incurred by the development process. 

\subsubsection{Value}

The value is defined under the assumption that more features developed mean that the software product is of higher value to its end users. Therefore, we approximate the value produced by the development process by the average throughput of features delivered per sprint, computed as

\begin{equation}
  \mathit{value} = \frac{F_\mathrm{completed}(T)}{T},
  \label{eq:obj_V}
\end{equation}

The $\mathit{value}$ should be \emph{maximised}. Thus, the goal is to develop as many features as possible within each sprint on average.

\subsubsection{Quality}

The quality of software is a second main criterion for end users: if the software is buggy, it will not be useful regardless of the number of features it has. We approximate quality by the average number of bugs that escaped to production per feature delivered, computed as
\begin{equation}
  \mathit{quality} = \frac{\omega_\mathrm{min}\,B_\mathrm{esc,min}(T)
          + \omega_\mathrm{maj}\,B_\mathrm{esc,maj}(T)
          + \omega_\mathrm{sec}\,B_\mathrm{esc,sec}(T)}
         {\max\!\bigl(1,\,F_\mathrm{completed}(T)\bigr)},
  \label{eq:obj_Q}
\end{equation}
where $\omega_\mathrm{min} \leq \omega_\mathrm{maj} \leq \omega_\mathrm{sec}$
are severity weights and the numerator covers all bugs that reached production
— both bugs that were never detected and bugs that were detected but not fixed
before their release deadline.
$\mathit{quality}$ measures the severity-weighted escaped-bug count per feature
delivered and is \emph{minimised}.


\subsubsection{Cost per feature}

The cost drivers are the human personnel costs and the agent API costs. We approximate the cost per feature delivered by the total cost incurred across the development cycle divided by the number of features delivered:
\begin{equation}
  \mathit{cost} = \frac{C_\mathrm{human} + C_\mathrm{agents}}
                       {\max\!\bigl(1,\,F_\mathrm{completed}(T)\bigr)},
  \label{eq:obj_CF}
\end{equation}
The $\mathit{cost}$ is \emph{minimised}.


The human personnel cost is the salary of the human developers. The parameter $c_\mathrm{salary}$ represents the annual fully-loaded salary of a human developer, defined for a period of 52 sprints (one sprint per week). The total human cost is computed by multiplying the number of developers $N$ by their salary, pro-rated over the $T$-sprint horizon:
\begin{equation}
  C_\mathrm{human} = N\,c_\mathrm{salary} \cdot \frac{T}{52}.
  \label{eq:cost_human}
\end{equation}

Each agent of role $k$ incurs a token cost $c_{\mathrm{token},k}$ per unit of
work produced $r_k$, e.g., per feature added, bug fixed, or test written. Thus, the costs are
computed with respect to throughput rates, rather than with a fixed rate per sprint.
The rational for this is practical: if we would charge a flat per-sprint fee for each agent, 
this would either assume that the costs are the same, regardless of the throughput or we would
need to model these costs as a function of the throughput. By modeling the costs, we decouple these
two aspects and allow independent settings of throughout and costs. 
We reusing the rates already introduced for the sprint
transition function where feasible (Table~\ref{tab:params:pipeline}), i.e., $r_1 = r_F$,
$r_2 = r_\mathrm{arch,chg}$, $r_4 = r_\mathrm{refactor}$, $r_7 = r_\mathrm{test}$,
and $r_8 = r_\mathrm{doc}$. The Bug Fixing Agent (role $k=3$) has three
severity-specific fix rates which we sum up, i.e., 
$r_3 = r_\mathrm{fix,min} + r_\mathrm{fix,maj} + r_\mathrm{fix,sec}$, the
agent's total bug-fixing throughput across all severities, as the rate for
costing purposes. The Code Review and Security Audit Agents ($k=5,6$) have no
throughput rate in the sprint transition function: they are assumed to have a fixed capacity,
which models the investment into these roles as a flat cost per agent per sprint. We therefore set
$r_5 = r_6 = 1$.

Because the development composition $\mathbf{A}_\mathrm{dev}$ and QA composition
$\mathbf{A}_\mathrm{qa}$ during a feature freeze differ, agent costs are split by phase: let $T_\mathrm{dev}$
and $T_\mathrm{qa} = T - T_\mathrm{dev}$ denote the number of development and
freeze sprints respectively. This gives us the agent costs
\begin{equation}
  C_\mathrm{agents} =
    \sum_{k=1}^{8} a_{\mathrm{dev},k}\,c_{\mathrm{token},k}\,r_k\,T_\mathrm{dev}
    + \sum_{k=1}^{8} a_{\mathrm{qa},k}\,c_{\mathrm{token},k}\,r_k\,T_\mathrm{qa}.
  \label{eq:cost_agents}
\end{equation}

% ---- 3.8 ----
\subsection{Monte Carlo Protocol}
\label{sec:model:mc}

A feasible configuration $\mathbf{c}$ (cf.\ Section~\ref{sec:model:mosp}) is evaluated by running $K$
independent Monte Carlo replications. At $t = 0$ all components of $S(0)$ must be initialised. We use fixed values to define the initial state of the system, e.g., zero features in the backlog and zero bugs in all queues.
These values define the state of the project when the first agentic development sprint
starts. They are fixed experiment constants that are
specified as part of the experiment design (see Section~\ref{sec:setup}). The
sprint transition $\mathcal{T}$ is then applied $T$ times, yielding terminal state
$S(T)$. The outcome of each simulation run is randomized by the actions within the sprint transition, which are driven by the stochastic processes, e.g., the Poisson feature arrivals and the Binomial bug detection draws.
The three Pareto objectives $(value_k, quality_k, cost_k)$ for each replication $k=1,\ldots,K$ are then computed from $S(T)$.

The objectives are aggregated across the $K$ replications to obtain point estimates and uncertainty quantification for each configuration. Point estimates are simply the averages across replications, i.e., the configuration performance is
summarised by the sample means $(\bar{value}, \bar{quality}, \bar{cost})$. The uncertainty is
quantified with 95\% percentile bootstrap confidence intervals (CIs):
$B = 1\,000$ bootstrap resamples of size $K$ (with replacement) are drawn from
the empirical replication distribution, and the 2.5th and 97.5th percentiles of
the bootstrap mean distribution give the interval endpoints. We use the bootstrap confidence intervals as a conservative decision rule for comparing configurations: only when the intervals of two configurations do not overlap do we treat their difference as statistically significant. Non-overlap of two 95\% confidence intervals is a stricter criterion than a hypothesis test at the 5\% level, so this rule errs on the side of treating configurations as equivalent.


% ---- 3.9 ----
\subsection{Multi-Objective Search Problem}
\label{sec:model:mosp}

The feasible set $\mathcal{F}$ is defined as the set of all configurations
$\mathbf{c} = (N,\,M,\,\mathbf{A}_\mathrm{dev},\,\mathbf{A}_\mathrm{qa},\,R,\,F_\mathrm{freeze})$
satisfying the structural constraints of Section~\ref{sec:model:team} and the
human-capacity feasibility condition of Eq.~\eqref{eq:feas_monitoring}.
The goal is to find a configuration in $\mathcal{F}$ that maximises $\mathit{value}$
while minimising $\mathit{quality}$ and $\mathit{cost}$:
\begin{equation}
  \min_{\mathbf{c}\,\in\,\mathcal{F}}\;(\mathit{quality},\,\mathit{cost}),\quad
  \max_{\mathbf{c}\,\in\,\mathcal{F}}\;\mathit{value}.
  \label{eq:pareto}
\end{equation}
Because the three objectives conflict — more agents raise $\mathit{value}$ but also
raise $\mathit{cost}$; stricter testing lowers $\mathit{quality}$ but consumes
agent capacity that could raise $\mathit{value}$ — no single configuration is
optimal on all three, and the solution is a Pareto frontier rather than a single point.


% ---- 3.10 ----
\subsection{CI-aware Pareto frontier}
\label{sec:model:pareto}

To account for the uncertainty of the software development process and the resulting Monte Carlo noise in the objective estimates, we establish the Pareto frontier with a CI-aware dominance rule.
The rule consists of two parts. The first is the commonly-used point-dominance relation, i.e., $\mathbf{c}$ \emph{point-dominates} $\mathbf{c}'$, iff
\begin{equation}
  \bar{v}_{\mathbf{c}} \ge \bar{v}_{\mathbf{c}'},\quad
  \bar{q}_{\mathbf{c}} \le \bar{q}_{\mathbf{c}'},\quad
  \bar{c}_{\mathbf{c}} \le \bar{c}_{\mathbf{c}'},
  \label{eq:point-dom}
\end{equation}
with at least one strict inequality.

The uncertainty-aware extension of this rule is that $\mathbf{c}$ is considered to dominate $\mathbf{c}'$ only if it also satisfies the second part of the rule, which is that $\mathbf{c}$ is \emph{CI-significantly better} than $\mathbf{c}'$ on at least one objective, established by at least one non-overlapping confidence interval:
\begin{equation}
  v^-_{\mathbf{c}} > v^+_{\mathbf{c}'}
  \quad\text{or}\quad
  q^+_{\mathbf{c}} < q^-_{\mathbf{c}'}
  \quad\text{or}\quad
  c^+_{\mathbf{c}} < c^-_{\mathbf{c}'}.
  \label{eq:ci-sig}
\end{equation}

Using these two rules, we define a CI-aware dominance relation: $\mathbf{c}$ \emph{CI-dominates} $\mathbf{c}'$ iff $\mathbf{c}$ point-dominates $\mathbf{c}'$ and $\mathbf{c}$ is CI-significantly better than $\mathbf{c}'$ on at least one objective. The Pareto frontier is then defined as the set of configurations that are not CI-dominated by any other configuration in the feasible set.

% ---- 3.11 ----
\subsection{Search Strategies for Pareto-Optimal Configurations}
\label{sec:model:search}

Exhaustive search of the configuration space for the Pareto frontier of optimal process and team configurations is infeasible due to the combinatorial explosion of possible configurations. For example, for a fixed
$(N, M)$ pair with agent budget $B = N \cdot M$, the number of non-negative
integer compositions of $B$ into 8 roles, $\binom{B+7}{7}$, is already
$\approx\!888\,000$ for $B = 20$ and $\approx\!63$ million for $B = 40$.
Across all choices of $N$, $M$, $R$, $F_\mathrm{freeze}$, and separate development
and QA compositions the full space is several orders of magnitude larger.

We therefore search $\mathcal{F}$ stochastically for Pareto-optimal configurations using two different approaches. Within both approaches, we first define a general search range for the parameters. \emph{Uniform random sampling} is our simple baseline strategy that randomly selects configurations uniformly from this search range. \emph{Evolutionary search} is a more sophisticated strategy that also starts with a uniform random sampling, but then looks for better configurations through evolutionary search.

\subsubsection{Search range}

The search range constrains four discrete parameters: the human developer count
$N \in \mathcal{N}$, the span of control $M \in \mathcal{M}$, the
release cadence $R \in \mathcal{R}$, and the feature-freeze length $F_\mathrm{freeze} \in \mathcal{F}_\mathrm{freeze}$.
The sets $\mathcal{N}$, $\mathcal{R}$, and $\mathcal{F}_\mathrm{freeze}$ are
explicit finite sets. This allows both the definition of ranges and of non-contiguous values, e.g., $\mathcal{N} = \{5, 10, 15\}$. The number of agents that each developer supervises is specified as a range $\mathcal{M} = \{1, \ldots, M_\mathrm{max}\}$.

While the agent compositions are also part of the search space,
there is no need to explicitly define their search range. Instead, the allowed values are implicitly
defined by the constraints of the simulation model. Once $N \in \mathcal{N}$ and $M \in \{1, \ldots, M_\mathrm{max}\}$ are fixed, there can be at most $N \cdot M$ agents in total. Additionally, the development composition $\mathbf{A}_\mathrm{dev}$ and the QA composition $\mathbf{A}_\mathrm{qa}$ must satisfy the structural constraints of Section~\ref{sec:model:team} and the human-capacity monitoring feasibility condition of Eq.~\eqref{eq:feas_monitoring}. These constraints implicitly define the allowed compositions for each $(N, M)$ pair, and therefore the search range for $\mathbf{A}_\mathrm{dev}$ and $\mathbf{A}_\mathrm{qa}$.
The feature-freeze duration is additionally constrained by the release cadence: once $R$ is sampled, only values from $\mathcal{F}_\mathrm{freeze}$ with $0 \leq F_\mathrm{freeze} \leq R-1$ are admissible.


\subsubsection{Uniform Random Search}
\label{sec:model:search:random}

In random search, each candidate configuration is drawn independently. A single candidate is generated using the following rejection sampling approach: 
\begin{enumerate}
  \item Draw $N, M, R$ uniformly from $\mathcal{N}$, $\mathcal{M}$, and $\mathcal{R}$ respectively.
  \item Draw $F_\mathrm{freeze}$ uniformly from the admissible values
        $\{f \in \mathcal{F}_\mathrm{freeze} : 0 \leq f \leq R-1\}$.
  \item Draw the development agent count $B_\mathrm{dev}$ uniformly from $\{1, \ldots, N \cdot M\}$
        and sample $\mathbf{A}_\mathrm{dev}$ as a composition such that $\sum_{k=1}^{8} a_{\mathrm{dev},k} = B_\mathrm{dev}$, with $a_{\mathrm{dev},1} \geq 1$.
  \item Draw the QA agent count $B_\mathrm{qa}$ uniformly from $\{0, \ldots, N \cdot M\}$
        and sample $\mathbf{A}_\mathrm{qa}$ as a QA-phase composition such that $\sum_{k=1}^{8} a_{\mathrm{qa},k} = B_\mathrm{qa}$, with $a_{\mathrm{qa},1} = a_{\mathrm{qa},2} = 0$.
  \item Discard the candidate if it violates the human-capacity feasibility condition of
        Eq.~\eqref{eq:feas_monitoring}.
\end{enumerate}

Using this approach, we draw $n_\mathrm{rand}$ random candidate configurations and evaluate each feasible candidate with $K$ Monte Carlo replications. The CI-aware Pareto frontier is then computed over the set of all evaluated configurations.

\subsubsection{Evolutionary Search}
\label{sec:model:search:evo}

While the random search strategy is simple and can discover diverse configurations, it is inefficient for finding Pareto-optimal configurations in a large search space: while the probability of randomly sampling something that is in the general area of the Pareto frontier is non-negligible, the probability of sampling a configuration that is actually on the Pareto frontier is low. 

We use an evolutionary search strategy to address this inefficiency. As a type of metaheuristic search, evolutionary search is designed to efficiently explore large, complex search spaces by iteratively generating and evaluating candidate solutions. By maintaining a population of candidate configurations and applying selection pressure toward better-performing configurations, evolutionary search can effectively navigate toward the Pareto frontier. In our case, we use a simple mutation-based algorithm that creates new solutions by modifying existing ones.

\paragraph{Initialisation.}
The evolutionary search starts with an initial pool $\mathcal{P}_0$ of $n_\mathrm{init}$ configurations. These configurations are generated using the same random sampling approach as in the random search strategy, ensuring that the initial pool is diverse and covers a broad area of the search space. Each configuration in the initial pool is evaluated with $K$ Monte Carlo replications. 

\paragraph{Mutation operator.}
The mutation operator receives a parent configuration
$\mathbf{c} = (N, M, \mathbf{A}_\mathrm{dev}, \mathbf{A}_\mathrm{qa}, R, F_\mathrm{freeze})$
and produces a child by perturbing exactly one randomly chosen parameter.
$R$ is never mutated, i.e., the release cadence is only sampled when generating the initial population.
The parameter to perturb is selected uniformly at random from five choices:
\begin{itemize}
  \item \emph{Mutate $N$:} replace the current value with an adjacent value in the
        discrete set $\mathcal{N}$ (the next smaller or larger element;
        a boundary value shifts inward).
  \item \emph{Mutate $M$:} increment $M$ by 1 if $M < M_\mathrm{max}$ and
        simultaneously add one agent to a randomly chosen role in $\mathbf{A}_\mathrm{dev}$,
        so that the expanded capacity $N \cdot M$ is immediately used during development sprints.
        Decreasing $M$ is excluded, because reducing the capacity bound without changing the compositions cannot alter simulation behaviour. 
  \item \emph{Mutate $F_\mathrm{freeze}$:} apply $\pm 1$ while ensuring that $F_\mathrm{freeze}$ stays in $[0, R-1]$.
  \item \emph{Mutate $\mathbf{A}_\mathrm{dev}$:} apply one elementary operation drawn uniformly from:
        \begin{itemize}
          \item \emph{Add}: increment one randomly chosen role by~1.
          \item \emph{Remove}: decrement one randomly chosen non-empty role by~1.
          \item \emph{Move}: select a random non-empty donor role and transfer one agent to a randomly chosen
                recipient role.
        \end{itemize}
  \item \emph{Mutate $\mathbf{A}_\mathrm{qa}$:} works the same as for $\mathbf{A}_\mathrm{dev}$, except that the implementation and architecture roles ($k = 1, 2$) remain fixed at zero.
\end{itemize}
If a mutation attempt produces an invalid configuration or leaves the parent unchanged
(e.g.\ because $M$ is already at $M_\mathrm{max}$, or a randomly chosen operation
is a structural no-op), the attempt is discarded and a new mutation type is drawn.
Up to ten attempts are made; if none yields a distinct valid child, the parent is
returned unchanged.

\paragraph{Generation loop.} The generation loop iteratively produces new configurations by mutating selected parents from the current pool of configurations. The loop is repeated for $g=1,\ldots,G$ generations. In each generation, the following steps are performed:
\begin{enumerate}
  \item Compute the current CI-aware Pareto frontier $\mathcal{F}_{g-1}$ over the previously generated population $\mathcal{P}_{g-1}$.
  \item Sample $n_\mathrm{off}$ parent configurations. 80\% of the parents are drawn uniformly from $\mathcal{F}_{g-1}$ to search for better solutions along the Pareto front. 20\% of the parents are drawn uniformly from $\mathcal{P}_{g-1} \setminus \mathcal{F}_{g-1}$ to enable exploration of the search space in other regions.
  \item Apply the mutation operator to each parent, creating the child population $\mathcal{P}_{g,child}$.
  \item Create the new population $\mathcal{P}_g$ as the union of the child population and the current population: $\mathcal{P}_g = \mathcal{P}_{g-1} \cup \mathcal{P}_{g,child}$.
\end{enumerate}

The mixture of drawing most mutations from the Pareto frontier and some from the rest of the population is designed to balance exploitation and exploration: the former focuses the search on improving the best-known configurations, while the latter allows for discovering new regions of the search space that may contain better configurations.

\paragraph{Final frontier.}
At the conclusion of the generation loop, the CI-aware Pareto frontier is computed over $\mathcal{P}_G$, which contains all feasible, simulated configurations evaluated across all generations.

\subsection{Scenarios}
\label{sec:setup:scenarios}

There are eight orthogonal aspects that influence our simulation, each governed by a distinct group of scenario parameters, i.e., the agent capabilitites and efforts, the human developer capabilities, the debt dynamics, the project dynamics, the agent costs, the human costs, and the bug impact. Each group contains multiple parameters that govern different facets of that aspect. For each of these aspects, we define three levels of parameters, corresponding to a low, medium, and high setting. For example, agent capabilities can be lower or higher, varying the number of features implemented per sprint by the implementation agents, the number of bugs fixed per sprint by the bug-fixing agents, and so on. Orthogonally, pricing of these agents can be cheaper or more expensive. Since they are orthogonal, we can freely combine all eight groups into a diverse set of scenarios. We use real-world data to ground the low/medium/high tiers of the eight scenario aspects. 

\subsubsection{Human developer parameters}

The scenario parameters for human developers are summarized in Table~\ref{tab:params:human}.
We assume that human developers work a 40-hour week and assume that the communication overhead is one hour per team member. We further assume that humans spent equal time bug fixing and implementing features within the time not required for other tasks. The salaries are estimated based on average salaries reported by Indeed~\citep{indeed2026salary}. We round low, average and high salaries to the next \$50k, to account for the employer overhead costs. 

While there is no data yet on how much time developers require to monitor agents, early results indicate that there is a fairly low interruption frequency~\Citep[prefix][postfix]{keylist}{baumann2026swechat}, so we set the monitoring overhead at a modest 2.5 hours per week, i.e., 30 minutes per day. These three variables are independent of developer skill and are therefore the same across all three tiers. There are also no estimates yet how much time developers require to resolve an agent escalation. It is reasonable to assume that these are non-trivial problems that require developers to get involved with the code base, so we assume that the time required is similar as to implement a feature (estimate see below).

We use the review of architectural decision records (ADRs) to ground the architecture-review time within our model. Amazon estimates 10-15 minutes to read the document~\citep{amazonArchitecturalDecision}. The process is assumed to be iterative and done by multiple developers. Assuming that updating the ADR based on comments requires 45 minutes, one iteration would require 1 hour. With 4 iterations, this would require a total of 4 hours, which we use for the medium tier. We assume that low capable developers require twice as long and highly capable developers are twice as fast, resulting in 8 hours for the low tier, and 2 hours for the high tier.

To have a comparable baseline for human effort, we assume the time required to solve SWE-bench Verified coding tasks, which are designed to be representative of real-world coding tasks by basing them on issues reported in open-source repositories~\citep{openai2026swebenchverified,jimenez2024swe}. We use METR's estimate for the human baseline of the time required to solve substantial issues within 1-4 hour time bucket of the benchmark, which estimates the time at 2 hours~\citep{kwa2026measuringaiabilitycomplete}. Since this seems reasonable, we use this for the medium tier. We use the pattern that low capable developers require twice as long as the medium tier and highly capable developers are twice as fast, resulting in 4 hours for the low tier, and 1 hour for the high tier. Since METR found that the $<15$ minute time bucket underestimates the time required to solve tasks, we instead use the 15 to 60 minute time bucket to estimate the time required to fix bugs in a similar manner, i.e., 30 minutes for the medium tier, 60 minutes for the low tier, and 15 minutes for the high tier. 

We estimate the bug introduction using the general defect density of software, which is estimated to be at about 4.3 per 1,000 \citep{shah2012overview}. Since SWE-Bench features change, on average, 107 lines of code~\cite{scaleSWEBenchPublic}, this translates to 0.44 bugs per feature, which we use as medium tier. We assume that low capable developers introduce twice as many bugs and highly capable developers introduce half as many, resulting in 0.88 bugs per feature for the low tier, and 0.22 bugs per feature for the high tier.

\subsubsection{Debt dynamics parameters}

There is a limited amount of literate on the impact of documentation and the studies are typically with small sets of developers, limiting their ability to find significant effects. \cite{dzidek2008uml} found an increase of mainetance time by 40\% when no UML documentation was made available based on a group of 20 developers. In a recent eye tracking experiment using 12 (mostly junior) developers, \cite{abdelsalam2026comments} found an increase in program comprehension time of up to 34\% based on code comments, but this effect dependend on the complexity of the code and comprehesion time was even reduced for simpler code snipptes. Based on these studies, we set the low tier to 0\% (no effect due to lack of significance of results), the medium tier to 34\% (the maximum effect found by \cite{abdelsalam2026comments}), and the high tier to 40\% (the effect found by \cite{dzidek2008uml}).

We estimate the addition of technical debt based on data from \cite{he2026cursordebt}, who found that AI-assisted coding increases code complexity and static analysis warnings. We note that this is particular for AI-assisted development as the technical debt otherwise seems to be decreasing over time \cite{trautsch2020longitudinal}. Since the average treatment effect found that AI-assisted developments leads to 28\% more lines, but 30\% more static analysis warnings, we assume that the debt increases by at least 2\% for every feature added. Since \cite{he2026cursordebt} also found that the complexity increase by 41\% due to the use of AI, we assume that the upper bound for the debt-increase is 13\% per feature added. We therefore set the low tier to 2\%, the medium tier to 6\% and the high tier to 13\% per feature added. Since \cite{trautsch2023automated} found that there is no detectable difference between the static analysis warnings added by bug fixing commits and other commits, we use the same values for the debt increase due to bug fixing.

We set the values for the maximum slow-down of maximal debt based on a developer survey from \cite{besker2018technical}. They found that developers spent on average 23\% of their time dealing with technical debt with a standard deviation of 17\%. We therefore set the low value at 6\% (i.e., one standard deviation below the average), the medium value at 23\% (the average), and the high value at 40\% (i.e., one standard deviation above the average). The work \cite{martini2027interest} found that technical debt can be contagious, which supports a non-linear effect of the technical debt. Since there is no data how strong this non-linearity is, we assume a slightly super-linear effect with $\delta_\mathrm{exp} = 1.5$ accross all scenarios.

\subsubsection{Agent costs and throughput parameters}

The agent cost parameters are summarized in Table~\ref{tab:params:costs}. While there is no direct scientific evidence for the exact costs per feature implementation, we assume that implementing a feature requires 100 tool calls and 2M cumulative input tokens, and 40k output tokens~\citep{morph2026aicodingcosts}. For bug fixes, we assume 25 tool calls, 400K cumulative input tokens, and 10K output tokens~\citep{morph2026aicodingcosts}. The costs for the other activities are grounded on these two costs:
\begin{itemize}
  \item Code review is assumed to be comparable to bug fixing, since similar analysis needs to be performed to understand the code and its implications. Security audits are more thourough and assumed to be ten times more expensive than normal code review.
  \item Architecture and design changes possibly require an analysis of the whole code base to understand the implications. Therefore, we assume that these carry high costs, comparable to the cost of implementing five features. 
  \item Refactoring is assumed to be comparable to implementing a feature, since it requires a similar amount of analysis and code changes.
  \item Writing tests and documentation are assumed to be comparable to bug fixing, since it requires a similar analysis of a local context.
\end{itemize} 
We further ground the pricing based on the API procing of Claude Sonnet, Opus, and Fable for low, medium, and high, respectively.

We model the throughput using the same assumptions on the relation between the throughput of the models as for the cost parameters, but base these estimations on the latency of the models, i.e., the time to solve a task. Since a concrete latency is hard to define as this depends not only on model size, but also on the current load of cloud providers, we do not estimate this on single latency values that are reported. Similar to other tasks, we ground this in SWE-Bench, where the reference solutions require 107 lines of code on average~\citep{scaleSWEBenchPublic}. Based on data from \cite{baumann2026swechat}, autonomous coding required 12.6 minutes on average per 100 commit lines. Assuming that agents only run during work hours, this would result in 190 features per sprint, resulting in the throughput rates reported in Table~\ref{tab:scenario:agents}.

We estimate the agentic bug introduction rate based on the SWE-bench Verfied benchmark score, assuming that each failure in the benchmark results in a bug in the code base. We collect the data for Claude 5 Sonnet, Opus, and Fable analogue to the cost estimations. The values are taken from the vals.ai leaderboard~\citep{valsai2026swebench}, i.e., we do not use the Anthropics estimates both those of independent benchmark executions. While we are aware that these results likely overestimate the actual benchmark performance~\citep{liang2026swe}, we nevertheless use this as (optimistic) estimate for the capabilities of the agents. 

We use CyberBench~\cite{liu2024cyberbench} to estimate the security bug introduction rate. While the benchmark is not a perfect fit, since it also includes the correction of the bug, it still gives us a good baseline for detection rate. For other benchmarks, like SEC-Bench Pro, we could not find data for recent models that is not self-reported by the model providers. Due to the model guardrails, we also cannot use the performance of the Claude 5 models here and instead use the GPT-5.6 models (Luna, Sol) and the scores reported by vals.ai~\citep{valsai2026cyberbench} for the medium and high tiers. Data for GPT-5.6 Terra is also not available, we therefore estiamte the the difference between Terra and Luna is the same as between Luna and Sol. We estimate the capability to generate tests based on data from \cite{huang2025benchmarking}, who developed a benchmark with unit tests for functions that were not part of the training. They found that test generation capability strongly correlates with coding ability, but models scored lower on the test generation benchmark, with differences of at least 0.2. Since no similar benchmark exists for the latest models, we assume that the trend holds and use the same difference here, i.e.,the SWE-bench scores reduced by 0.2. 

We use SWE-Review~\citep{wang2026swe} to estimate how good language models are at code review. Within this benchmark, Claude Opus 4.6 was able to correctly judge pull requests for between 75\% and 89\% of the cases. We use these as low and high tier respectively and use the mid-point 0.82 for the medium tier.

Finally, we estimate the escalation rate based on telemetry data from \cite{baumann2026swechat}: in their study, the agents escalated between 1\% and 3\% of the time, which we use as low and high tier respectively. We use the mid-point 0.02 for the medium tier.
