\section{Introduction}
\label{sec:introduction}

\begin{quote}
  \textit{If that \$500000 engineer did not consume at least \$250000 worth of tokens, I am going to be deeply alarmed} --- Jensen Huang, CEO of Nvidia (March, 2026).
\end{quote}

Agentic AI systems based on Large Language Models (LLMs) -- hereafter refered to as agents -- have been shown to have strong capabilties in software engineering tasks, including code generation~\citep{TODO}, code review~\citep{TODO}, bug fixing~\citep{TODO}, and test generation~\citep{TODO}. This led to a rapid adoption of these agents in software development teams~\cite{TODO}. Recently, the uncritical adoption and unrestricted use of these agents is being roled back, not least due to the spiraling costs~\citep{TODO}. Such problems are not unexpected with new technology, where we are still trying to understand all implications. Nevertheless, this raises the question is Jensen Huang's general estimate that developers should consume at least half of their salary in agent tokens is reasonable, or whether there are better ways to compose human and agent workforces. This is the central research question of this work:

\begin{description}
  \item[RQ] How should software development teams compose their human and agent workforce to achieve the best trade-off between value, quality, and cost?
\end{description}

To answer this question, we develop a simulation model of mixed AI-human software development teams. The core assumption of our process is that the human is still owning the code, takes responsibility for the quality, and guides the key design decisions. Agents support the human by implementing features, fixing bugs, and providing quality assurance, while also draining resources from the human developers because they require supervision. We simulate the development as a stochastic process that evolves over multiple sprints, where each sprint represents a fixed-duration development iteration. Within each sprint, human developers and agents implement features and fix bugs. Agents may fail at this task which escalates the responsibility for addressing an issue to the human developers. The new bugs, that are introduced through the development, can be detected by agents that review code, audit for security issues, and generate tests.
Through these activities, new bugs are introduced, which agents can detect by providing tests or reviewing code. Large changes to the architecture require the sign-of by the human developers. 

The model is based on a discrete-time stochastic dynamical system that simulates the evolution of a software project over multiple sprints. The state of the project is represented by a 21-dimensional vector that tracks features, bugs, technical debt, and human capacity. The model incorporates eight specialist AI agent roles and one human developer role, each with specific functions and interactions. The simulation allows for different team compositions and process parameters, enabling the exploration of trade-offs between value, quality, and cost.

\section{Model Description}
\label{sec:model}
% ============================================================

The model treats software development as a discrete-time stochastic dynamical
system. The simulation runs for $T$ sprints; each sprint represents one
fixed-duration iteration. States are indexed $t \in \{0, 1, \ldots, T\}$,
where $S(0)$ is the fixed initial state (before any sprint executes) and
$S(t)$ for $t \geq 1$ is the state produced by sprint $t$. The simulation
horizon is $T$. The simulation configuration is defined by the team composition and process parameters 
$\mathbf{c} = (N, \mathbf{A}_\mathrm{dev}, \mathbf{A}_\mathrm{qa}, R, F_\mathrm{freeze})$. The parameters
$N$, $\mathbf{A}_\mathrm{dev}$, $\mathbf{A}_\mathrm{qa}$ define the team structure (Section~\ref{sec:model:roles}). The parameters $R$ and $F_\mathrm{freeze}$ define the release cycle and feature freezes (Section~\ref{sec:model:cycle}). The team composition further depends on whether the current sprint is in the development phase or the feature freeze phase of the release cycle (Section~\ref{sec:model:team}). The development team of humans and agents evolves a software project whose state at sprint $t$ is represented by a 21-dimensional state vector $S(t)$ defined in Section~\ref{sec:model:state}. Scenario parameters govern the behavior of the underlying software development process and the capabilities of the agents, such as feature throughput rates, bug injection rates, bug detection probabilities, and cost coefficients (Section~\ref{sec:model:parameters}). The transition from $S(t-1)$ to $S(t)$ is governed by the sprint dynamics $\mathcal{T}$, which consists of ten ordered steps (Section~\ref{sec:model:transition}).

We can derive metrics that describe the utility of a team configuration using three objectives (Section~\ref{sec:model:objectives}): the $value$ as the average number of features completed per sprint, the $quality$ as the average number of escaped bugs per completed feature, and the $cost$ as the average cost incurred per completed feature. By exploring different team and process configurations $\mathbf{c}$, we get a multi-objective search problem with the goal to identify optimal configurations with different trade-offs between the objectives (Section~\ref{sec:model:mosp}). By running multiple simulations with different random seeds for each configuration $\mathbf{c}$, we can establish the uncertainty of the simulation through a Monte Carlo approach and estimate the confidence intervals of the objectives (Section~\ref{sec:model:mc}). The outcomes for different configurations form a Pareto frontier that characterises the trade-offs between the objectives and provides practical guidance on how to compose mixed AI-human teams for software development (Section~\ref{sec:model:pareto}). Since the search space is combinatorial and high-dimensional, we further describe different search strategies to efficiently explore the space of valid configurations (Section~\ref{sec:model:search}).

\subsection{Roles}
\label{sec:model:roles}



There is only a single human role included in the model: the \textit{Human
Developer}. Developers communicate with each other, supervise agents,
review and approve architecture proposals, resolve
escalations that agents cannot handle autonomously, and contribute new
features and bug fixes with the remaining time.

We do not assume that developers dedicate all of their time to the project. $N$ is therefore
not a headcount but a \emph{staffing level} measured in full-time equivalents (FTE), and it
need not be an integer: $N = 0.25$ describes one developer who devotes a quarter of their
working time to the project, and $N = 2.5$ describes two full-time developers plus one
half-time developer. Accordingly, $H_\mathrm{capacity}$ is the gross time budget of one FTE
per sprint, so that the gross budget available to the whole team is $N \cdot
H_\mathrm{capacity}$ hours per sprint.

We have eight specialist AI agent roles, indexed $k = 1,\ldots,8$. All agents of the
same type are assumed to be statistically identical. We further distinguish between agents that
require supervision and agents that run fully autonomously. The supervised agents consume monitoring capacity from
the human developers but are otherwise assumed to execute tasks autonomously. Table~\ref{tab:roles} summarises each AI agent role's primary function.

The eight roles fall into three functional groups. The production roles
(k = 1,\ldots,4) all directly contribute to the production code. 
The \textit{Feature Implementation Agent} is the primary
productivity driver implementing features and architecture changes. While doing so, the agent also generates
architecture change requests and introduces new bugs into the codebase.
The \textit{Architecture Agent} creates proposals for architecture updates for human review. Neglecting architecture change requests degrades internal quality and will lead to architectural debt accumulation.
The \textit{Bug Fixing Agent} drains the known-bug
queue. The work conducted by the Feature Implementation and Bug Fixing Agents introduces technical debt.
The \textit{Refactoring Agent} improves the internal quality of the system autonomously and reduces technical debt.
From a conceptual perspective, the \textit{Architecture Agent} is responsible for high-stakes structural changes that require human review, while the \textit{Refactoring Agent} is responsible for low-stakes internal improvements that can be executed autonomously without review. 

The review roles (k = 5,6) inspect
every code change synchronously in the same sprint as injection. The \textit{Code Review
Agent} detects all kinds of defects but gets less effective if there is more code to review. The \textit{Security Audit Agent} can only detect security defects and allows the modeling of more expensive agents for this high-stakes role; it degrades with the review volume and with technical debt in the same way as the Code Review Agent. These two agents run autonomously, i.e., the human developers do not need to supervise them and detected issues are automatically added to the bug queues.
The \textit{Test Development Agent} (k = 7) builds up a continuously growing test suite, which helps detect bugs.

Finally, there is one \emph{support role} (k = 8): the \textit{Developer Documentation Agent} creates documentation to aid human developers, which in turn reduces the
per-agent monitoring overhead that consumes human capacity by reducing the cognitive load
of the human developers when supervising agents.

\subsection{Release Cycle and Feature Freezes}
\label{sec:model:cycle}

A release occurs exactly at sprint indices $R, 2R, 3R, \ldots$ where $R \geq 1$
is the fixed release cadence. At each release, unfixed bugs (both hidden and known)
escape to production, incrementing the cumulative escaped bug counters. 
Similar to real-world projects, a feature freeze is implemented to stabilise the
codebase before release. The feature freeze lasts for $F_\mathrm{freeze} \in
[0, R-1]$ sprints before a release.
Sprint $t$ is in the freeze window iff $((t-1) \bmod R) \geq R - F_\mathrm{freeze}$, i.e., the freeze window comprises the last $F_\mathrm{freeze}$ sprints of each release cycle, including the release sprint itself.

Each sprint selects the active agent composition based on its
position in the release cycle: the \emph{development composition}
is used during the first $R - F_\mathrm{freeze}$
sprints of each cycle; the \emph{QA composition} is
used during the remaining $F_\mathrm{freeze}$ sprints. The different compositions allow a different focus,
i.e., focus on feature addition versus focus on quality assurance and bug fixing.

\subsection{Project and team structure}
\label{sec:model:team}

Given the above description of the roles and release cycle, we can now specify the project and team structure using five control variables: the human staffing level in FTE
$N \in \mathbb{R}_{>0}$, the number of sprints per release $R \geq 1$, the length of the feature freeze period $F_\mathrm{freeze} \in
[0, R-1]$, and two 8-element agent composition vectors $\mathbf{A}_\mathrm{dev}$ and
$\mathbf{A}_\mathrm{qa}$ described below.

$\mathbf{A}_\mathrm{dev} = (a_{dev,1},\ldots,a_{dev,8}) \in \mathbb{N}_{\geq 0}^{8}$ is the
development-phase composition and $\mathbf{A}_\mathrm{qa} = (a_{qa,1},\ldots,a_{qa,8}) \in \mathbb{N}_{\geq 0}^{8}$ is the QA composition. As established in Section~\ref{sec:model:roles}, the roles split into two tiers with respect to human oversight: the \emph{supervised} roles
$\mathcal{K}_\mathrm{sup} = \{1,2,3,4,7,8\}$ and the two autonomous review services
$\mathcal{K}_\mathrm{bg} = \{5,6\}$. We write
\begin{equation}
  n_\mathrm{sup}(t) = \sum_{k \in \mathcal{K}_\mathrm{sup}} a_{\cdot,k}
  \label{eq:nsup}
\end{equation}
for the number of active supervised agents in sprint $t$. Every supervised agent consumes monitoring effort from the human developers, so the admissible compositions are limited by the human-capacity feasibility condition of Section~\ref{sec:model:transition}, Eq.~\eqref{eq:feas_monitoring}. Leaving supervised slots unfilled may be optimal in some cases to reduce coordination overhead and free up human capacity for review, escalation, and implementation work.
The counts $a_{\cdot,5}$ and $a_{\cdot,6}$ of the background services are unbounded, since these agents require no supervision and therefore consume no human monitoring capacity. The only brake on them is their token cost, since at some point investing more in detecting possible bugs yields diminishing returns. The dev-phase and QA-phase counts are independent of each other, so a service can be staffed differently during a feature freeze than during development.
$\mathbf{A}_\mathrm{dev}$ must satisfy $a_{dev,1} \geq 1$, i.e., there must be at least one Feature
Implementation Agent in the development phase. This also ensures that there is $value$, i.e., that at least some features are implemented and the simulation does not trivially collapse to zero throughput.
For $F_\mathrm{freeze} \geq 1$, $\mathbf{A}_\mathrm{qa}$ is required to have $a_{qa,1} = a_{qa,2} = 0$, to ensure that no new features are added during a feature freeze and that all agents are redeployed to QA roles. If $F_\mathrm{freeze}=0$, the QA composition is never active and has no effect on the simulation.

\subsection{State Space}
\label{sec:model:state}

$S(t)$ denotes the 21-component system state produced by sprint $t$ (for $t \geq 1$); $S(0)$ is the fixed initial state. The components fall into four
clusters summarised in Table~\ref{tab:state}: two variables that describe the features in the backlog and completed; twelve variables that track bugs in their various stages; five variables that track technical debt and human capacity queues; and two variables that track test infrastructure and documentation coverage.

\subsubsection{Feature pipeline}
$F_\mathrm{backlog}(t) \in \mathbb{N}_{\geq 0}$ counts features awaiting
implementation after sprint $t$ completed. Within each sprint, this queue grows governed by the configuration parameters (see Section~\ref{sec:model:parameters}), while the \textit{Feature Implementation Agents} and the
direct coding capacity of \textit{Human Developers} reduce the value of pending features by implementing them and thereby growing the monotonically increasing cumulative count of fully implemented features $F_\mathrm{completed}(t) \in \mathbb{N}_{\geq 0}$.

\subsubsection{Bug queues}

Our simulation model distinguishes between three mutually exclusive bug types: \emph{minor}, \emph{major}, and \emph{security} bugs. Configuration parameters determine the impact of the different bug types on quality and the rates at which bugs of the different types are introduced, relative to each other (see Section~\ref{sec:model:parameters}). The bugs are tracked at four queue kinds — hidden, known, released, and escaped — and each
kind maintains one counter per type, giving twelve bug state variables in total.

$B_\mathrm{hid,x}(t)$ (for $x \in \{\mathrm{min, maj, sec}\}$) counts type-$x$ bugs
that have been injected in the current release cycle but not been detected yet.
$B_\mathrm{kno,x}(t)$ counts type-$x$ bugs that have been detected and are queued for
repair. The separation between hidden and known is load-bearing: fixing capacity is
consumed only by detected bugs, while hidden bugs silently degrade quality. $B_\mathrm{esc,x}(t) \in \mathbb{N}_{\geq 0}$ is the
monotonically increasing cumulative count of type-$x$ bugs that reached production.
Since escaped bugs must still be fixed, $B_\mathrm{rel,x}(t)$ counts the subset of
escaped type-$x$ bugs still open at the start of sprint $t$; these are served with
priority by the Bug Fixing Agent ahead of the known-bug queue.

\subsubsection{Technical debt and human capacity queues.}

$D_\mathrm{tech}(t) \in [0, 1]$ is a normalised measure of technical debt: $D_\mathrm{tech} = 0$ represents
a debt-free codebase and $D_\mathrm{tech} = 1$ represents maximum degradation. $D_\mathrm{tech}(t)$ can be reduced autonomously by the \textit{Refactoring Agent}. $Q_\mathrm{arch}(t) \in \mathbb{N}_{\geq 0}$ counts the architecture change requests that are still pending, $Q_\mathrm{rev}(t) \in \mathbb{N}_{\geq 0}$ counts the architecture proposals awaiting human review, and $Q_\mathrm{arch,impl}(t) \in \mathbb{N}_{\geq 0}$ counts the approved architecture proposals that are awaiting implementation. Together, these three variables measure the architectural degradation, which requires human intervention to be reduced and cannot be reduced fully autonomously. $Q_\mathrm{esc}$ is the agent escalation queue: agents may fail to implement a feature on their own and need to escalate this to a human developer to resolve the issue. 

All these variables grow with the work of the Feature Implementation Agents and the Bug Fixing Agents, which introduce technical debt and generate architecture change requests as they implement features and fix bugs. Thus, faster development speed directly increases the accumulation of technical debt, architectural debt, and escalation requests.

\subsubsection{Test infrastructure and documentation.}

We assume that there is a continuous integration system in place that automatically runs a test suite to detect
bugs. The status of this test suite is tracked by $N_\mathrm{test}(t)$, which is the cumulative number of tests written by the Test
Development Agent. New tests are added every sprint to increase the \emph{test coverage} $\mathrm{cov\_test}$, which is derived from the test count and the number of implemented features as
\begin{equation}
  \mathrm{cov\_test}(t) = \min\!\left(c_\mathrm{test,ceil},\;
    \frac{N_\mathrm{test}(t)}{\max\!\bigl(1,\,F_\mathrm{completed}(t)\bigr)}\right),
  \label{eq:coverage}
\end{equation}
Higher coverage increases the likelihood that introduced defects are detected to move bugs from the hidden to the known queues. 

Similarly, $N_\mathrm{doc}(t)$ is the cumulative number of documentation items produced by
the Developer Documentation Agent and grows monotonically each sprint.
Documentation \emph{coverage} is derived from this count relative to
$F_\mathrm{completed}(t-1)$ in the same way as test coverage:
\begin{equation}
  \mathrm{doc\_cov}(t-1) = \min\!\left(1,\;
    \frac{N_\mathrm{doc}(t-1)}{\max\!\bigl(1,\,F_\mathrm{completed}(t-1)\bigr)}\right),
  \label{eq:doc_cov}
\end{equation}
capped at 1, i.e.\ full documentation coverage.
The $t-1$ index reflects that the documentation is updated at the end of the sprint, i.e., the new documentation only becomes available in the next sprint. This means that the benefits of documentation investment (i.e., reduced monitoring effort for human developers) are always lagged by one sprint.

\subsection{Configuration Parameters}
\label{sec:model:parameters}

The behavior of the agents and the simulation model in each sprint
is governed by a set of parameters that must be defined before running the simulation. 
The parameters codify the assumptions about the underlying software development process and the capabilities of the agents, and they determine how the state variables evolve over time. They can be grouped into human-capacity parameters (Table~\ref{tab:params:human}), feature-pipeline and throughput-rate parameters (Table~\ref{tab:params:pipeline}), bug-injection parameters (Table~\ref{tab:params:injection}), quality assurance parameters for bug detection (Table~\ref{tab:params:detection}), technical-debt parameters (Table~\ref{tab:params:debt}), and cost parameters (Table~\ref{tab:params:costs}). The tables describe the meaning of each parameter, its domain, and which step of the sprint transition first uses it (see Section~\ref{sec:model:transition} for the step definitions). How exactly each of the parameters is used is described in Section~\ref{sec:model:transition}; how we initialize them will be discussed as part of the experiments (see Section~\ref{sec:setup}).

\subsection{Sprint Transition Function}
\label{sec:model:transition}

The sprint transition $\mathcal{T}: S(t-1) \to S(t)$ executes ten steps in
fixed dependency order. 

% TODO: Figure 3 -- data-flow diagram of the 10-step transition

\subsubsection*{Step 1 --- Human Capacity Allocation}

The priority-ordered time budget of the developers is
resolved as a five-stage cascade, each stage consuming time that is remaining from the previous stage. First, communication overhead between the developers reduces capacity to
\begin{equation}
  H_\mathrm{net} = H_\mathrm{capacity} - c_\mathrm{comm}\lceil N-1 \rceil
  \label{eq:hnet}
\end{equation}
per FTE. Communication is a per-person cost that does not shrink when a person invests only
part of their time in the project, so the overhead is driven by the headcount rather than by
the staffing level. $\lceil N \rceil$ is the smallest
headcount that can supply $N$ FTE. Since $n_\mathrm{sup}(t)$ is the number of active supervised agents, each FTE supervises
$\frac{n_\mathrm{sup}(t)}{N}$ agents, consuming $\frac{n_\mathrm{sup}(t)}{N} \cdot H_\mathrm{mon,eff}(t)$ hours of monitoring effort. The per-agent monitoring effort is reduced by the documentation coverage $\mathrm{doc\_cov}(t-1)$ (from the previous sprint) and the reduction is calibrated by $\Gamma_\mathrm{doc}$
\begin{equation}
  H_\mathrm{mon,eff}(t) = H_\mathrm{mon,overhead}\,
    \bigl(1 - \Gamma_\mathrm{doc}\,\mathrm{doc\_cov}(t-1)\bigr),
  \label{eq:hmoneff}
\end{equation}
leaving post-monitoring capacity
\begin{equation}
  H_\mathrm{after\_mon}(t) = \max\!\Bigl(0,\; H_\mathrm{net} -
    \frac{n_\mathrm{sup}(t)}{N}\,H_\mathrm{mon,eff}(t)\Bigr).
  \label{eq:hafter_mon}
\end{equation}
We assume $\Gamma_\mathrm{doc} \leq 1$, so that documentation reduces, but never inverts, the monitoring effort.

Architecture reviews are served from this remainder and drain the architecture review queue $Q_\mathrm{rev}(t-1)$ at rate
$N/H_\mathrm{review\_time}$:
\begin{align}
  \mathrm{rev\_done}(t) &= \min\!\Bigl(
    \bigl\lfloor H_\mathrm{after\_mon}(t)\cdot N\,/\,H_\mathrm{review\_time}\bigr\rfloor,\;
    Q_\mathrm{rev}(t-1)\Bigr),
  \label{eq:rev_done}
\end{align}
leaving post-review capacity
\begin{equation}
  H_\mathrm{after\_rev}(t) =
    H_\mathrm{after\_mon}(t) - \mathrm{rev\_done}(t)\,H_\mathrm{review\_time}/N.
  \label{eq:hafter_rev}
\end{equation}
Escalations are served analogously:
\begin{equation}
  \mathrm{esc\_done}(t) = \min\!\Bigl(
    \bigl\lfloor H_\mathrm{after\_rev}(t)\cdot N\,/\,H_\mathrm{esc\_time}\bigr\rfloor,\;
    Q_\mathrm{esc}(t-1)\Bigr),
  \label{eq:esc_done}
\end{equation}
leaving post-escalation capacity
\begin{equation}
  H_\mathrm{after\_esc}(t) =
    H_\mathrm{after\_rev}(t) - \mathrm{esc\_done}(t)\,H_\mathrm{esc\_time}/N.
  \label{eq:hafter_esc}
\end{equation}
The remaining capacity $H_\mathrm{after\_esc}(t)$ is used for coding:
fraction $f_\mathrm{fix}$ goes to bug fixing and $(1-f_\mathrm{fix})$ to feature implementation:
\begin{align}
  \mathrm{fix\_human}(t)  &=
    \bigl\lfloor N\,f_\mathrm{fix}\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{fix}\bigr\rfloor,
  \label{eq:fixhuman} \\
  \mathrm{impl\_human}(t) &=
    \bigl\lfloor N\,(1-f_\mathrm{fix})\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{feature}\bigr\rfloor.
  \label{eq:implhuman}
\end{align}
During feature-freeze sprints (Section~\ref{sec:model:cycle}), $\mathrm{impl\_human}=0$ and
all of $H_\mathrm{after\_esc}(t)$ is redirected to bug fixing:
\begin{equation}
  \mathrm{fix\_human}(t)\big|_\mathrm{freeze} =
    \bigl\lfloor N\,H_\mathrm{after\_esc}(t)\,/\,h_\mathrm{fix}\bigr\rfloor.
  \label{eq:fixhuman_freeze}
\end{equation}
Both activities are debt-independent: $h_\mathrm{feature}$ and $h_\mathrm{fix}$ are fixed
costs regardless of the current debt level $D_\mathrm{tech}(t-1)$. While not fully realistic, this assumption simplifies the model and assumes that human effort includes dealing with possibly existing debt-related complexity. 

$H_\mathrm{after\_mon}(t)$ is driven to zero if monitoring overhead exceeds $H_\mathrm{net}$.
Configurations for which this is unavoidable cannot perform any productive human work regardless of the scenario-parameter draws. We therefore define a feasibility criterion that is checked before running the simulation for the development composition $\mathbf{A}_\mathrm{dev}$, and for the QA composition $\mathbf{A}_\mathrm{qa}$ when $F_\mathrm{freeze} \geq 1$:
\begin{align}
  H_\mathrm{net} = H_\mathrm{capacity} - c_\mathrm{comm}\lceil N-1 \rceil &\geq 0 \\
  \frac{\sum_{k \in \mathcal{K}_\mathrm{sup}} a_{\cdot,k}}{N}\,H_\mathrm{mon,overhead}\,
    (1 - \Gamma_\mathrm{doc}) &< H_\mathrm{net}.
  \label{eq:feas_monitoring}
\end{align}
This check ensures that the developers have sufficient capacity for the communication between
themselves and for the monitoring of agents under the best-case assumption of perfect documentation coverage. The criterion is a necessary condition rather than a sufficient one: since the documentation coverage starts below its ceiling, the effective monitoring overhead early in a simulation run can still temporarily exceed the available capacity. We do not specify similar constraints for architecture review and escalation time, as not handling these only increases the debt penalties we discuss next, meaning that implementation is still possible, though less efficient.

\subsubsection*{Step 2 --- Debt Penalties}

Technical debt $D_\mathrm{tech}$, as well as unresolved work in the architecture
and escalation pipelines contribute to productivity degradation.
Architecture work is considered unresolved as long as it remains anywhere in
the pipeline: as an unprocessed change request ($Q_\mathrm{arch}$), as a design
proposal awaiting human review ($Q_\mathrm{rev}$), or as an approved proposal
awaiting implementation ($Q_\mathrm{arch,impl}$). We normalize this by the team's \emph{maximum throughput} for the
corresponding human activity in one sprint
$H_\mathrm{capacity} \cdot N \;/\; H_{x}$.
A value of~1 means the queue holds as many items as the team could process in
an entire sprint under ideal conditions, i.e., the team would need a full sprint just to drain the queue. Once the queue reaches this or a worse state, the architectural degradation has reached its maximum. Step~2 reads queue values carried over from sprint $t-1$, so all debt quantities use the $t-1$ index. Overall, this gives us the architectural debt as
\begin{equation}
  D_\mathrm{arch}(t-1) = \min\!\Bigl(1,\;
    \frac{Q_\mathrm{arch}(t-1) + Q_\mathrm{rev}(t-1) + Q_\mathrm{arch,impl}(t-1)}
         {H_\mathrm{capacity}\,N \;/\; H_\mathrm{review\_time}}\Bigr).
  \label{eq:D_arch}
\end{equation}
A long escalation queue likewise signals a team under strain: unresolved
escalations indicate that agents require frequent human intervention, which
degrades coordination quality.  Normalising by the maximum escalation throughput
$H_\mathrm{capacity}\,N / H_\mathrm{esc\_time}$ gives
\begin{equation}
  D_\mathrm{esc}(t-1) = \min\!\Bigl(1,\;
    \frac{Q_\mathrm{esc}(t-1)}
         {H_\mathrm{capacity}\,N \;/\; H_\mathrm{esc\_time}}\Bigr).
  \label{eq:D_esc}
\end{equation}
The combined effective debt is
\begin{equation}
  D_\mathrm{eff}(t-1) = \min\!\bigl(1,\; D_\mathrm{tech}(t-1) + D_\mathrm{arch}(t-1) + D_\mathrm{esc}(t-1)\bigr).
  \label{eq:D_eff}
\end{equation}
The \emph{debt amplifier}
\begin{equation}
  \delta_D = 1 - (1 - \delta_\mathrm{min})\,D_\mathrm{eff}(t-1)^{\delta_\mathrm{exp}}
  \label{eq:delta_D}
\end{equation}
is a single function of the combined debt, parameterised by a floor
$\delta_\mathrm{min} \in (0,1)$ that describes the highest negative impact the debt can have and shape exponent $\delta_\mathrm{exp} > 0$ that controls the rate of decay.
It equals~1 at zero combined debt and decays to $\delta_\mathrm{min}$ at
$D_\mathrm{eff} = 1$. This debt multiplier will be used in subsequent steps to reduce feature implementation speed, increase bug injection, reduce code review quality, slow bug fixing, and increase the rate at which agents require escalations.

\subsubsection*{Step 3 --- Feature Arrival and Implementation}
In every sprint, new features arrive to the backlog according to
\begin{equation}
  \mathrm{arrivals}(t) \sim \mathrm{Poisson}(r_\mathrm{arrival}),
  \label{eq:arrivals}
\end{equation}
growing the backlog at the beginning of the step. Because arrivals are added before implementation runs, newly arrived features are immediately available for implementation in the same sprint. The backlog is then drained by human and agent implementation.

Available agent capacity is first consumed by approved architecture proposals
$Q_\mathrm{arch,impl}(t-1)$ pending implementation, with remaining capacity applied
to the feature backlog. Writing
$\mathrm{demand}(t) = F_\mathrm{backlog}(t-1) + \mathrm{arrivals}(t)$ for the features
available for implementation, the human developers are served first and the agents
implement what remains. The rational for this is that the human salary has to be paid so their capacity should be used first.
\begin{align}
  \mathrm{arch\_impl}(t) &= \min\!\Bigl(Q_\mathrm{arch,impl}(t-1),\;
    \bigl\lfloor r_F\,\delta_D\,a_1\bigr\rfloor\Bigr),
  \label{eq:arch_impl} \\
  \mathrm{impl\_human}'(t) &= \min\!\bigl(\mathrm{impl\_human}(t),\;\mathrm{demand}(t)\bigr),
  \label{eq:impl_human_capped} \\
  \mathrm{impl\_agents}(t) &= \min\!\Bigl(\mathrm{demand}(t) - \mathrm{impl\_human}'(t),\;
    \bigl\lfloor r_F\,\delta_D\,a_1\bigr\rfloor - \mathrm{arch\_impl}(t)\Bigr).
  \label{eq:impl_agents}
\end{align}
Implementing approved architecture proposals ($\mathrm{arch\_impl}$) consumes agent
capacity but does not increment $F_\mathrm{completed}$, since it represents internal
architecture work rather than user-visible feature delivery. The feature implementation is linearly reduced by $\delta_D$ to reflect the impact of debt on development speed.
Total user-feature implementation per sprint is capped at the available backlog to
prevent over-counting features:
\begin{equation}
  \mathrm{impl}(t) = \mathrm{impl\_agents}(t) + \mathrm{impl\_human}'(t)
    \;\leq\; \mathrm{demand}(t),
  \label{eq:impl}
\end{equation}
and the state variables are updated as:
\begin{align}
  F_\mathrm{backlog}(t)   &= F_\mathrm{backlog}(t-1) + \mathrm{arrivals}(t) - \mathrm{impl}(t),
    \label{eq:backlog_update} \\
  F_\mathrm{completed}(t) &= F_\mathrm{completed}(t-1) + \mathrm{impl}(t).
    \label{eq:completed_update}
\end{align}

\subsubsection*{Step 4 --- Test Suite Update}
The Test Development Agent grows the
cumulative test count before bug detection runs, up to the coverage ceiling of
Eq.~\eqref{eq:coverage}, beyond which further tests no longer raise
$\mathrm{cov\_test}$:
\begin{equation}
  N_\mathrm{test}(t) = \min\!\bigl(N_\mathrm{test}(t-1) + r_\mathrm{test}\,a_7,\;
    c_\mathrm{test,ceil}\,F_\mathrm{completed}(t)\bigr).
  \label{eq:ntest_update}
\end{equation}
Because this step executes before bug injection and detection (Step~5), the new
tests written this sprint are immediately available to raise the test coverage
$\mathrm{cov\_test}$. Investment in testing therefore
pays off in the sprint it occurs, creating a direct incentive to allocate
agents to the Test Development role.

\subsubsection*{Step 5 --- Bug Injection and Detection}
Each implemented feature injects defects at an effective per-feature rate
\begin{equation}
  r_\mathrm{bugs,eff}(t) = r_\mathrm{bugs}\,(2 - \delta_D),
  \label{eq:r_bugs_eff}
\end{equation}
where the factor $(2 - \delta_D) \in [1,\, 2 - \delta_\mathrm{min}]$ increases the bug injection as debt accumulates.
Bugs are drawn in two independent Poisson streams -- one for
agent-implemented features and one for human-implemented features -- and
then summed:
\begin{align}
  B_\mathrm{agents}(t) &\sim
    \mathrm{Poisson}\!\bigl(\mathrm{impl\_agents}(t)\cdot r_\mathrm{bugs,eff}(t)\bigr),
    \nonumber \\
  B_\mathrm{human}(t)  &\sim
    \mathrm{Poisson}\!\bigl(\mathrm{impl\_human}'(t)\cdot r_\mathrm{bugs,eff}(t)
      \cdot r_\mathrm{bugs,human}\bigr),
    \nonumber \\
  B_\mathrm{inj}(t)    &= B_\mathrm{agents}(t) + B_\mathrm{human}(t),
  \label{eq:Binj}
\end{align}
where $r_\mathrm{bugs,human}$ reflects the ratio of defect density of
human-written code relative to agent-generated code.

Each injected bug is assigned to exactly one of three mutually exclusive types via
a sequential draw: security bugs are extracted first, then the remainder is split
into major and minor:
\begin{align}
  B_\mathrm{sec}(t) &\sim \mathrm{Binomial}\!\bigl(B_\mathrm{inj}(t),\;\theta_\mathrm{sec}\bigr),
    \nonumber \\
  B_\mathrm{maj}(t) &\sim \mathrm{Binomial}\!\Bigl(B_\mathrm{inj}(t)-B_\mathrm{sec}(t),\;
    \tfrac{\theta_\mathrm{maj}}{\theta_\mathrm{min}+\theta_\mathrm{maj}}\Bigr),
    \nonumber \\
  B_\mathrm{min}(t) &= B_\mathrm{inj}(t) - B_\mathrm{sec}(t) - B_\mathrm{maj}(t),
  \label{eq:type_split}
\end{align}
where $\theta_\mathrm{min} = 1 - \theta_\mathrm{maj} - \theta_\mathrm{sec}$.

Detection proceeds in three sequential stages that model a workflow where first an existing test suite is run against code
changes (simulating a CI pipeline), then code review is conducted, and finally a security audit is performed by a specialist agent. 

The test suite detects bugs at rate
\begin{equation}
  p_\mathrm{test}(t) = \min\!\bigl(1,\; d_\mathrm{test}\,\mathrm{cov\_test}(t)\bigr),
  \label{eq:p_test}
\end{equation}
where $\mathrm{cov\_test}(t)$ is given by Eq.~\eqref{eq:coverage}. 

Within our model, we assume that both agents invest effort that is reasonable to review a single feature in depth. If more features need to be reviewed, the per-feature review effectiveness is reduced. We model this through a degradation function $\Phi$ of the number of features relative to the number of agents. We use a logarithmic transformation to model this as diminishing returns:
\begin{equation}
  \Phi(v, a) =
  \begin{cases}
    \max\!\Bigl(0,\; 1 - \alpha_\mathrm{size}\log\!\bigl(\tfrac{v}{a} + 1\bigr)\Bigr) & a \geq 1,\\[4pt]
    0 & a = 0.
  \end{cases}
  \label{eq:volume_factor}
\end{equation}
The code review then detects bugs that survive testing at effective rate
\begin{equation}
  d_\mathrm{CR,eff}(t) = d_\mathrm{CR}\,\delta_D\,\Phi\bigl(\mathrm{impl}(t),\, a_{\cdot,5}\bigr),
  \label{eq:dcr_eff}
\end{equation}
and the Security Audit Agent detects the security bugs that survive both earlier stages at rate
\begin{equation}
  d_\mathrm{SA,eff}(t) = d_\mathrm{SA}\,\delta_D\,\Phi\bigl(\mathrm{impl}(t),\, a_{\cdot,6}\bigr).
  \label{eq:dsa_eff}
\end{equation}

Let $T_x(t)$, $C_x(t)$ denote the counts detected by tests and code review for type
$x$, and $A_\mathrm{sec}(t)$ the count detected by the security audit. These are given by binomial draws with the corresponding detection probabilities:
\begin{align}
  T_x(t)        &\sim \mathrm{Binomial}\!\bigl(B_x(t),\; p_\mathrm{test}(t)\bigr),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  C_x(t)        &\sim \mathrm{Binomial}\!\bigl(B_x(t)-T_x(t),\; d_\mathrm{CR,eff}(t)\bigr),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  A_\mathrm{sec}(t) &\sim \mathrm{Binomial}\!\bigl(B_\mathrm{sec}(t)-T_\mathrm{sec}(t)-C_\mathrm{sec}(t),\; d_\mathrm{SA,eff}(t)\bigr).
    \nonumber
\end{align}
The known and hidden queues are incremented accordingly:
\begin{align}
  B_\mathrm{kno,x}(t)   &= B_\mathrm{kno,x}(t-1) + T_x(t) + C_x(t),
    & x &\in \{\mathrm{min,maj}\}, \label{eq:bkno_update} \\
  B_\mathrm{kno,sec}(t) &= B_\mathrm{kno,sec}(t-1) + T_\mathrm{sec}(t) + C_\mathrm{sec}(t) + A_\mathrm{sec}(t),
    \nonumber \\
  B_\mathrm{hid,x}(t)   &= B_\mathrm{hid,x}(t-1) + B_x(t) - T_x(t) - C_x(t),
    & x &\in \{\mathrm{min,maj}\}, \nonumber \\
  B_\mathrm{hid,sec}(t) &= B_\mathrm{hid,sec}(t-1) + B_\mathrm{sec}(t) - T_\mathrm{sec}(t) - C_\mathrm{sec}(t) - A_\mathrm{sec}(t).
    \nonumber
\end{align}
Note that $B_\mathrm{kno,x}(t)$ is an intermediate value at this step, which will be decreased by the bug fixing conducted in Step~7. 

\subsubsection*{Step 6 --- Architecture Queues}
This step propagates architecture work through three queues $Q_\mathrm{arch}$, $Q_\mathrm{rev}$, and $Q_\mathrm{arch,impl}$ in causal order. First, we determine how many new architecture change requests are generated by the features implemented this sprint.
Architecture change requests are generated at rate $f_\mathrm{arch,chg}$ per
feature implemented this sprint,
giving Poisson-distributed arrivals that fill the change-request queue:
\begin{align}
  \mathrm{arch\_chg\_new}(t) &\sim \mathrm{Poisson}\!\bigl(f_\mathrm{arch,chg}\cdot\mathrm{impl}(t)\bigr) \\
  Q_\mathrm{arch}(t) &= Q_\mathrm{arch}(t-1) + \mathrm{arch\_chg\_new}(t).
  \label{eq:arch_chg_new}
\end{align}

Then, the Architecture Agents drain $Q_\mathrm{arch}$ at rate $r_\mathrm{arch,chg}$ per agent.
Each resolved change request produces one design proposal forwarded to the human
review queue $Q_\mathrm{rev}$, which is at the same time reduced by the human review capacity:
\begin{align}
  \mathrm{arch\_chg\_done}(t) &= \min\!\bigl(Q_\mathrm{arch}(t),\;
    \lfloor r_\mathrm{arch,chg}\,a_2\rfloor\bigr), \label{eq:arch_chg_done} \\
  Q_\mathrm{arch}(t) &= Q_\mathrm{arch}(t) - \mathrm{arch\_chg\_done}(t),
    \label{eq:Q_arch} \\
  Q_\mathrm{rev}(t) &= \max\!\bigl(0,\;
    Q_\mathrm{rev}(t-1) + \mathrm{arch\_chg\_done}(t) - \mathrm{rev\_done}(t)\bigr).
    \label{eq:Q_rev}
\end{align}

Finally, the $\mathrm{rev\_done}(t)$ proposals reviewed and approved this sprint are placed
into the \emph{architecture implementation queue} $Q_\mathrm{arch,impl}$, enabling their implementation in the next sprint by the Implementation Agents in Step~3:
\begin{equation}
  Q_\mathrm{arch,impl}(t) = \max\!\bigl(0,\;
    Q_\mathrm{arch,impl}(t-1) + \mathrm{rev\_done}(t) - \mathrm{arch\_impl}(t)\bigr).
  \label{eq:Q_arch_impl}
\end{equation}

\subsubsection*{Step 7 --- Bug Fixing}
Bug fixing proceeds in two phases using the same six priority tiers
($B_\mathrm{rel,sec} \to B_\mathrm{kno,sec} \to B_\mathrm{rel,maj} \to
B_\mathrm{kno,maj} \to B_\mathrm{rel,min} \to B_\mathrm{kno,min}$):

\emph{Phase 1 — Human fixes (debt-independent):} Human developers apply their
bug-fixing budget $\mathrm{fix\_human}(t)$ to the priority tiers in order. Each bug fixed
consumes one unit of the integer budget, so:
\begin{equation}
  n^H_i(t) = \min\!\Bigl(\text{queue}_i(t),\; B^H_i(t)\Bigr),
  \qquad B^H_{i+1}(t) = B^H_i(t) - n^H_i(t),
  \label{eq:human_fixes}
\end{equation}
where $B^H_1(t) = \mathrm{fix\_human}(t)$.

\emph{Phase 2 — Agent fixes (debt-slowed):} The Bug Fixing Agents then drain the
remaining queues, traversing the same tiers in the same order with a shared budget
\begin{equation}
  B^A_1(t) = \bigl\lfloor a_3\,\delta_D\,r_\mathrm{fix}\bigr\rfloor,
  \label{eq:fix_budget}
\end{equation}
i.e., the per-agent fix rate $r_\mathrm{fix}$ scaled by the number of deployed Bug Fixing
Agents and by the debt amplifier $\delta_D$. As for the humans, each bug fixed consumes one
unit of this budget, irrespective of its severity:
\begin{align}
  n^A_i(t) &= \min\!\Bigl(\text{queue}_i(t) - n^H_i(t),\; B^A_i(t)\Bigr),
  \label{eq:fixes} \\
  B^A_{i+1}(t) &= B^A_i(t) - n^A_i(t). \nonumber
\end{align}
The two phases therefore differ only in how their budget is derived: the human budget follows
from the available human capacity and is debt-independent, whereas the agent budget scales with
the number of deployed agents and shrinks as technical debt accumulates.
Since human fixes take priority, a well-staffed team can
shield the known-bug queue from debt effects even when $\delta_D$ is low.

Letting $n_i(t) = n^H_i(t) + n^A_i(t)$ denote the total bugs fixed from tier $i$
across both phases, the release and known-bug queues are decremented:
\begin{align}
  B_\mathrm{rel,sec}(t) &= B_\mathrm{rel,sec}(t-1) - n_1(t), \nonumber \\
  B_\mathrm{kno,sec}(t) &= B_\mathrm{kno,sec}(t)   - n_2(t), \nonumber \\
  B_\mathrm{rel,maj}(t) &= B_\mathrm{rel,maj}(t-1) - n_3(t), \nonumber \\
  B_\mathrm{kno,maj}(t) &= B_\mathrm{kno,maj}(t)   - n_4(t), \nonumber \\
  B_\mathrm{rel,min}(t) &= B_\mathrm{rel,min}(t-1) - n_5(t), \nonumber \\
  B_\mathrm{kno,min}(t) &= B_\mathrm{kno,min}(t)   - n_6(t).
  \label{eq:bfix_update}
\end{align}
The $B_\mathrm{rel,x}$ rows use index $t-1$ on the right because the release
queues are not written by any earlier step in this sprint.  The $B_\mathrm{kno,x}$
rows use index $t$ as a reminder that their right-hand side values
were already updated by Step~5.

\subsubsection*{Step 8 --- Escalation Queue}
Agents raise human escalations per completed work item at rate $\rho_\mathrm{esc}$.
The work the supervised agents completed this sprint is
\begin{equation}
  W_\mathrm{agent}(t) = \mathrm{impl\_agents}(t) + \mathrm{arch\_chg\_done}(t)
    + \mathrm{fixes\_agent}(t),
  \label{eq:w_agent}
\end{equation}
where $\mathrm{fixes\_agent}(t) = \sum_{i=1}^{6} n^A_i(t)$ is the agent share of the
repairs of Step~7. Human work is excluded, since a developer does not escalate to
themselves, as are the two background services, which file findings rather than
escalating. New arrivals each sprint are then
$\mathrm{esc\_new}(t) \sim \mathrm{Poisson}\bigl(\rho_\mathrm{esc}\,(2-\delta_D)\,W_\mathrm{agent}(t)\bigr)$,
where the factor $(2 - \delta_D)$ increases the escalation rate as debt accumulates, as
it does for bug injection in Eq.~\eqref{eq:r_bugs_eff}. The queue is then updated taking
the capacity for human escalation resolution $\mathrm{esc\_done}(t)$ into account:
\begin{equation}
  Q_\mathrm{esc}(t) = \max\!\bigl(0,\;
    Q_\mathrm{esc}(t-1) + \mathrm{esc\_new}(t) - \mathrm{esc\_done}(t)\bigr),
  \label{eq:qesc}
\end{equation}

\subsubsection*{Step 9 --- General Maintenance}
Subsequent to the feature implementation, testing, and bug fixing steps, the general maintenance
agents perform their work. They do not provide direct utilitarian value in the form of features delivered or bugs fixed, but instead provide indirect value by slowing the accumulation of technical debt and by improving the documentation, which reduces the cognitive load of the human developers when supervising agents.

The first such activity is performed by the Refactoring Agent, which reduces technical debt. 
Three activities drive the technical debt $D_\mathrm{tech}(t)$: feature implementation and
bug fixing each \emph{increase} debt, while refactoring conducted by the Refactoring Agent 
\emph{decreases} it.
\begin{equation}
\begin{split}
  D_\mathrm{tech}(t) = \operatorname{clip}\bigl(D_\mathrm{tech}(t-1)
    &+ \delta_\mathrm{impl}\,\mathrm{impl}(t) \\
    &+ \delta_\mathrm{fix}\,\mathrm{fixes\_total}(t) \\
    &- r_\mathrm{refactor}\,a_4,\; 0,\, 1\bigr),
  \label{eq:debt_update}
\end{split}
\end{equation}
where $\mathrm{fixes\_total}(t) = \sum_{i=1}^{6} n_i(t)$ is the total number of bugs fixed across all priority tiers in Step~7.

The second activity is documentation written by the Developer Documentation Agent which grows the cumulative
document count, up to one document per completed feature, i.e., the point at which
Eq.~\eqref{eq:doc_cov} is capped:
\begin{equation}
  N_\mathrm{doc}(t) = \min\!\bigl(N_\mathrm{doc}(t-1) + r_\mathrm{doc}\,a_8,\;
    F_\mathrm{completed}(t)\bigr).
  \label{eq:ndoc_update}
\end{equation}
This increases the documentation coverage $\mathrm{doc\_cov}$ in the next
sprint (see Eq.~\eqref{eq:doc_cov}).

\subsubsection*{Step 10 --- Release Event}
If $t \bmod R = 0$, a release fires: all bugs remaining in the hidden and known queues
escape to production: bugs that were never detected as well as bugs that were detected but not fixed before the release deadline.
These bugs are added to the cumulative escaped counter
and to the in-production repair queue. Afterwards, the hidden and known queues are reset to zero:
\begin{align}
  B_\mathrm{esc,x}(t)  &= B_\mathrm{esc,x}(t-1) + B_\mathrm{hid,x}(t) + B_\mathrm{kno,x}(t),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{rel,x}(t)  &= B_\mathrm{rel,x}(t)   + B_\mathrm{hid,x}(t) + B_\mathrm{kno,x}(t),
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{hid,x}(t)  &= 0,
    & x &\in \{\mathrm{min,maj,sec}\}, \nonumber \\
  B_\mathrm{kno,x}(t)  &= 0,
    & x &\in \{\mathrm{min,maj,sec}\}.
  \label{eq:release_update}
\end{align}
The $B_\mathrm{rel,x}$ rows use the unindexed $t$ form on the right because the
release queue was already updated by Step~7 (bug fixing) within this sprint;
similarly $B_\mathrm{kno,x}(t)$ on the right is the post-fixing value from
Steps~5 and~8. When $t \bmod R \neq 0$ no release fires and all updates are skipped.

\subsection{Objective Functions}
\label{sec:model:objectives}

The model is designed to evaluate the Pareto trade-offs between three key objectives: value, quality, and costs. These objectives are computed at the end of the $T$-sprint simulation horizon and effectively aggregate performance across the entire development cycle. The main criteria are the value approximated by the number of features that were developed, the quality approximated by the number of bugs that escaped to production, and the total cost incurred by the development process. 

\subsubsection{Value}

The value is defined under the assumption that more features developed mean that the software product is of higher value to its end users. Therefore, we approximate the value produced by the development process by the average throughput of features delivered per sprint, computed as

\begin{equation}
  \mathit{value} = \frac{F_\mathrm{completed}(T)}{T},
  \label{eq:obj_V}
\end{equation}

The $\mathit{value}$ should be \emph{maximised}. Thus, the goal is to develop as many features as possible within each sprint on average.

\subsubsection{Quality}

The quality of software is a second main criterion for end users: if the software is buggy, it will not be useful regardless of the number of features it has. We approximate quality by the average number of bugs that escaped to production per feature delivered, computed as
\begin{equation}
  \mathit{quality} = \frac{\omega_\mathrm{min}\,B_\mathrm{esc,min}(T)
          + \omega_\mathrm{maj}\,B_\mathrm{esc,maj}(T)
          + \omega_\mathrm{sec}\,B_\mathrm{esc,sec}(T)}
         {\max\!\bigl(1,\,F_\mathrm{completed}(T)\bigr)},
  \label{eq:obj_Q}
\end{equation}
where $\omega_\mathrm{min} \leq \omega_\mathrm{maj} \leq \omega_\mathrm{sec}$
are severity weights and the numerator covers all bugs that reached production
— both bugs that were never detected and bugs that were detected but not fixed
before their release deadline.
$\mathit{quality}$ measures the severity-weighted escaped-bug count per feature
delivered and is \emph{minimised}.


\subsubsection{Cost per feature}

The cost drivers are the human personnel costs and the agent API costs. We approximate the cost per feature delivered by the total cost incurred across the development cycle divided by the number of features delivered:
\begin{equation}
  \mathit{cost} = \frac{C_\mathrm{human} + C_\mathrm{agents}}
                       {\max\!\bigl(1,\,F_\mathrm{completed}(T)\bigr)},
  \label{eq:obj_CF}
\end{equation}
The $\mathit{cost}$ is \emph{minimised}.


The human personnel cost is the salary of the human developers. The parameter $c_\mathrm{salary}$ represents the annual fully-loaded salary of a human developer, defined for a period of 52 sprints (one sprint per week). The total human cost is computed by multiplying the number of developers $N$ by their salary, pro-rated over the $T$-sprint horizon:
\begin{equation}
  C_\mathrm{human} = N\,c_\mathrm{salary} \cdot \frac{T}{52}.
  \label{eq:cost_human}
\end{equation}

Each agent of role $k$ incurs a token cost $c_{\mathrm{token},k}$ per unit of
work produced $r_k$, e.g., per feature added, bug fixed, or test written. Thus, the costs are
computed with respect to throughput rates, rather than with a fixed rate per sprint.
The rationale for this is practical: if we would charge a flat per-sprint fee for each agent, 
this would either assume that the costs are the same, regardless of the throughput or we would
need to model these costs as a function of the throughput. By modeling the costs, we decouple these
two aspects and allow independent settings of throughput and costs. 
We reuse the rates already introduced for the sprint
transition function where feasible (Table~\ref{tab:params:pipeline}), i.e., $r_1 = r_F$,
$r_2 = r_\mathrm{arch,chg}$, $r_3 = r_\mathrm{fix}$, $r_4 = r_\mathrm{refactor}$,
$r_7 = r_\mathrm{test}$, and $r_8 = r_\mathrm{doc}$. The Code Review and Security Audit Agents ($k=5,6$) have no
throughput rate in the sprint transition function, because they run as background services with no discrete unit of output: each deployed instance inspects whatever change volume the sprint produces. We therefore set
$r_5 = r_6 = 1$, which charges the investment into these roles as a flat subscription fee per deployed instance per sprint. Note that this makes the cost of these roles linear in their headcount, while their detection benefit is concave in the headcount by Eq.~\eqref{eq:volume_factor}. This trade-off is what bounds the number of these agents in an optimal configuration, even though the model imposes no explicit cap on them.

Agents are therefore charged for the work they actually performed, so that an agent that
no work reaches incurs no cost. Let $u_k(t)$ denote the work role $k$ completed in sprint
$t$, measured in the unit of that role's rate $r_k$ and read off the sprint transition as
summarised in Table~\ref{tab:work_units}. Implementing an approved architecture proposal is
billed as five feature implementations, since it requires the same code-base-wide analysis
that makes an architecture proposal five times as expensive to produce (Section~\ref{sec:scenario:agentcosts}). This gives us the
agent costs
\begin{equation}
  C_\mathrm{agents} = \sum_{k=1}^{8} c_{\mathrm{token},k} \sum_{t=1}^{T} u_k(t).
  \label{eq:cost_agents}
\end{equation}

\subsection{Monte Carlo Protocol}
\label{sec:model:mc}

A feasible configuration $\mathbf{c}$ (cf.\ Section~\ref{sec:model:mosp}) is evaluated by running $K$
independent Monte Carlo replications. At $t = 0$ all components of $S(0)$ must be initialised. We use fixed values to define the initial state of the system, e.g., zero features in the backlog and zero bugs in all queues.
These values define the state of the project when the first agentic development sprint
starts. They are fixed experiment constants that are
specified as part of the experiment design (see Section~\ref{sec:setup}). The
sprint transition $\mathcal{T}$ is then applied $T$ times, yielding terminal state
$S(T)$. The outcome of each simulation run is randomized by the actions within the sprint transition, which are driven by the stochastic processes, e.g., the Poisson feature arrivals and the Binomial bug detection draws.
The three Pareto objectives $(value_k, quality_k, cost_k)$ for each replication $k=1,\ldots,K$ are then computed from $S(T)$.

The objectives are aggregated across the $K$ replications to obtain point estimates and uncertainty quantification for each configuration. Point estimates are simply the averages across replications, i.e., the configuration performance is
summarised by the sample means $(\bar{value}, \bar{quality}, \bar{cost})$. The uncertainty is
quantified with 95\% percentile bootstrap confidence intervals (CIs):
$B = 1\,000$ bootstrap resamples of size $K$ (with replacement) are drawn from
the empirical replication distribution, and the 2.5th and 97.5th percentiles of
the bootstrap mean distribution give the interval endpoints. We use the bootstrap confidence intervals as a conservative decision rule for comparing configurations: only when the intervals of two configurations do not overlap do we treat their difference as statistically significant. Non-overlap of two 95\% confidence intervals is a stricter criterion than a hypothesis test at the 5\% level, so this rule errs on the side of treating configurations as equivalent.


% ---- 3.9 ----
\subsection{Multi-Objective Search Problem}
\label{sec:model:mosp}

The feasible set $\mathcal{F}$ is defined as the set of all configurations
$\mathbf{c} = (N,\,\mathbf{A}_\mathrm{dev},\,\mathbf{A}_\mathrm{qa},\,R,\,F_\mathrm{freeze})$
satisfying the structural constraints of Section~\ref{sec:model:team} and the
human-capacity feasibility condition of Eq.~\eqref{eq:feas_monitoring}.
The goal is to find a configuration in $\mathcal{F}$ that maximises $\mathit{value}$
while minimising $\mathit{quality}$ and $\mathit{cost}$:
\begin{equation}
  \min_{\mathbf{c}\,\in\,\mathcal{F}}\;(\mathit{quality},\,\mathit{cost}),\quad
  \max_{\mathbf{c}\,\in\,\mathcal{F}}\;\mathit{value}.
  \label{eq:pareto}
\end{equation}
Because the three objectives conflict — more agents raise $\mathit{value}$ but also
raise $\mathit{cost}$; stricter testing lowers $\mathit{quality}$ but consumes
agent capacity that could raise $\mathit{value}$ — no single configuration is
optimal on all three, and the solution is a Pareto frontier rather than a single point.


% ---- 3.10 ----
\subsection{CI-aware Pareto frontier}
\label{sec:model:pareto}

To account for the uncertainty of the software development process and the resulting Monte Carlo noise in the objective estimates, we establish the Pareto frontier with a CI-aware dominance rule.
The rule consists of two parts. The first is the commonly-used point-dominance relation, i.e., $\mathbf{c}$ \emph{point-dominates} $\mathbf{c}'$, iff
\begin{equation}
  \bar{v}_{\mathbf{c}} \ge \bar{v}_{\mathbf{c}'},\quad
  \bar{q}_{\mathbf{c}} \le \bar{q}_{\mathbf{c}'},\quad
  \bar{c}_{\mathbf{c}} \le \bar{c}_{\mathbf{c}'},
  \label{eq:point-dom}
\end{equation}
with at least one strict inequality.

The uncertainty-aware extension of this rule is that $\mathbf{c}$ is considered to dominate $\mathbf{c}'$ only if it also satisfies the second part of the rule, which is that $\mathbf{c}$ is \emph{CI-significantly better} than $\mathbf{c}'$ on at least one objective, established by at least one non-overlapping confidence interval:
\begin{equation}
  v^-_{\mathbf{c}} > v^+_{\mathbf{c}'}
  \quad\text{or}\quad
  q^+_{\mathbf{c}} < q^-_{\mathbf{c}'}
  \quad\text{or}\quad
  c^+_{\mathbf{c}} < c^-_{\mathbf{c}'}.
  \label{eq:ci-sig}
\end{equation}

Using these two rules, we define a CI-aware dominance relation: $\mathbf{c}$ \emph{CI-dominates} $\mathbf{c}'$ iff $\mathbf{c}$ point-dominates $\mathbf{c}'$ and $\mathbf{c}$ is CI-significantly better than $\mathbf{c}'$ on at least one objective. The Pareto frontier is then defined as the set of configurations that are not CI-dominated by any other configuration in the feasible set.

% ---- 3.11 ----
\subsection{Search Strategies for Pareto-Optimal Configurations}
\label{sec:model:search}

Exhaustive search of the configuration space for the Pareto frontier of optimal process and team configurations is impossible, because the counts of the two background services are unbounded (Section~\ref{sec:model:team}). Even under an arbitrary cap of 99 agents per service, the four background counts $a_{\mathrm{dev},5}$, $a_{\mathrm{dev},6}$, $a_{\mathrm{qa},5}$, and $a_{\mathrm{qa},6}$ alone already give $100^4 = 10^8$ combinations, which the human staffing level, the release cadence, the feature-freeze length, and the supervised parts of both compositions multiply further.

We therefore search $\mathcal{F}$ stochastically for Pareto-optimal configurations using two different approaches. Within both approaches, we first define a general search range for the parameters. \emph{Uniform random sampling} is our simple baseline strategy that randomly selects configurations uniformly from this search range. \emph{Evolutionary search} is a more sophisticated strategy that also starts with a uniform random sampling, but then looks for better configurations through evolutionary search.

\subsubsection{Search range}

The search range constrains three discrete parameters: the human staffing level
$N \in \mathcal{N}$, the
release cadence $R \in \mathcal{R}$, and the feature-freeze length $F_\mathrm{freeze} \in \mathcal{F}_\mathrm{freeze}$.
The sets $\mathcal{N}$, $\mathcal{R}$, and $\mathcal{F}_\mathrm{freeze}$ are
explicit finite sets. This allows both the definition of ranges and of non-contiguous values, e.g., $\mathcal{N} = \{0.5, 1, 2\}$.

Once $N \in \mathcal{N}$ is fixed, the development composition $\mathbf{A}_\mathrm{dev}$ and the QA composition $\mathbf{A}_\mathrm{qa}$ must satisfy the structural constraints of Section~\ref{sec:model:team} and the human-capacity monitoring feasibility condition of Eq.~\eqref{eq:feas_monitoring}. However, there is a further constraint that the model implicitly imposes: The effort that every supervised role can contribute is restricted by the amount of work that reaches it, which is all derived from the feature arrival rate $r_\mathrm{arrival}$. While this is trivially the case for the implementation agent through Equations~\eqref{eq:impl_agents} and \eqref{eq:impl}, the architecture work, bug fixing, refactoring, test development, and documentation are also bounded by the inflow of work that reaches them (see Eqs.~\eqref{eq:arch_chg_done}, \eqref{eq:r_bugs_eff}, \eqref{eq:debt_update}, \eqref{eq:coverage}, and \eqref{eq:doc_cov}). This gives us the following fixed-point upper bounds on the work that can reach each supervised role in one development sprint, expressed relative to the feature arrival rate $r_\mathrm{arrival}$:
\begin{align}
  W_1 &= (1 + f_\mathrm{arch,chg})\,r_\mathrm{arrival}, &
  W_2 &= f_\mathrm{arch,chg}\,r_\mathrm{arrival}, \nonumber\\
  W_3 &= r_\mathrm{bugs}\,(2-\delta_\mathrm{min})\,r_\mathrm{arrival}, &
  W_4 &= \delta_\mathrm{impl}\,r_\mathrm{arrival} + \delta_\mathrm{fix}\,W_3, \nonumber\\
  W_7 &= c_\mathrm{test,ceil}\,r_\mathrm{arrival}, &
  W_8 &= r_\mathrm{arrival}.
  \label{eq:workload}
\end{align}
The workload is matched against the throughput that an agent can have, accounting for the debt amplifier, we use its floor $\delta_\mathrm{min}$, i.e., the least favourable and therefore most permissive case:
\begin{equation}
  \begin{aligned}
    \rho_1 &= r_F\,\delta_\mathrm{min}, &
    \rho_2 &= r_\mathrm{arch,chg}, &
    \rho_3 &= r_\mathrm{fix}\,\delta_\mathrm{min}, \\
    \rho_4 &= r_\mathrm{refactor}, &
    \rho_7 &= r_\mathrm{test}, &
    \rho_8 &= r_\mathrm{doc}.
  \end{aligned}
  \label{eq:sat_rates}
\end{equation}

The two background detection services are not constrained at all, so instead of a search range we specify a sampling distribution for them below. The feature-freeze duration is additionally constrained by the release cadence: once $R$ is sampled, only values from $\mathcal{F}_\mathrm{freeze}$ with $0 \leq F_\mathrm{freeze} \leq R-1$ are admissible.

This gives us constraints
\begin{equation}
  a_{\mathrm{dev},k},\, a_{\mathrm{qa},k} \;\leq\; u_k
    = \Bigl\lceil \sigma\,\frac{W_k}{\rho_k} \Bigr\rceil,
  \qquad k \in \mathcal{K}_\mathrm{sup}.
  \label{eq:sat_bound}
\end{equation}
where $\sigma \geq 1$ is a headroom factor that allows the search to explore configurations that exceed the steady-state workload, which means that the agent capacity can be overallocated to a certain degree to deal with load peaks that can occur due to the Poisson feature arrivals. We do not distinguish between the development and QA compositions here. Taken together with the feasible set of Section~\ref{sec:model:mosp}, this defines the region that the search strategies explore:
\begin{equation}
  \mathcal{S} = \bigl\{\mathbf{c} \in \mathcal{F} \;:\;
    a_{\mathrm{dev},k} \leq u_k \;\wedge\;
    a_{\mathrm{qa},k} \leq u_k
    \;\;\forall k \in \mathcal{K}_\mathrm{sup} \bigr\} \subseteq \mathcal{F}.
  \label{eq:searched_region}
\end{equation}


\subsubsection{Uniform Random Search}
\label{sec:model:search:random}

In random search, each candidate configuration is drawn independently. A single candidate is generated using the following rejection sampling approach: 
\begin{enumerate}
  \item Draw $N$ and $R$ uniformly from $\mathcal{N}$ and $\mathcal{R}$ respectively.
  \item Draw $F_\mathrm{freeze}$ uniformly from the admissible values
        $\{f \in \mathcal{F}_\mathrm{freeze} : 0 \leq f \leq R-1\}$.
  \item Draw the supervised part of $\mathbf{A}_\mathrm{dev}$ role by role, independently and
        uniformly within the throughput saturation bound of Eq.~\eqref{eq:sat_bound}, i.e.,
        $a_{\mathrm{dev},1}$ from $\{1, \ldots, u_1\}$ so that
        $a_{\mathrm{dev},1} \geq 1$, and $a_{\mathrm{dev},k}$ from
        $\{0, \ldots, u_k\}$ for the remaining $k \in \mathcal{K}_\mathrm{sup}$.
  \item Draw the supervised part of $\mathbf{A}_\mathrm{qa}$ in the same way, i.e.,
        $a_{\mathrm{qa},k}$ uniformly from $\{0, \ldots, u_k\}$ for
        $k \in \{3,4,7,8\}$, and $a_{\mathrm{qa},1} = a_{\mathrm{qa},2} = 0$.
  \item Draw the four background service counts $a_{\mathrm{dev},5}$, $a_{\mathrm{dev},6}$,
        $a_{\mathrm{qa},5}$, $a_{\mathrm{qa},6}$ independently and uniformly from
        $\{0, 1, \ldots, \lfloor r_\mathrm{arrival} \rfloor\}$, i.e., we allow up to one instance
        of each service per feature that arrives in a sprint.
  \item Discard the candidate if it violates the human-capacity feasibility condition of
        Eq.~\eqref{eq:feas_monitoring}.
\end{enumerate}

Using this approach, we draw $n_\mathrm{rand}$ random candidate configurations and evaluate each feasible candidate with $K$ Monte Carlo replications. The CI-aware Pareto frontier is then computed over the set of all evaluated configurations.

\subsubsection{Evolutionary Search}
\label{sec:model:search:evo}

While the random search strategy is simple and can discover diverse configurations, it is inefficient for finding Pareto-optimal configurations in a large search space: while the probability of randomly sampling something that is in the general area of the Pareto frontier is non-negligible, the probability of sampling a configuration that is actually on the Pareto frontier is low. 

We use an evolutionary search strategy to address this inefficiency. As a type of metaheuristic search, evolutionary search is designed to efficiently explore large, complex search spaces by iteratively generating and evaluating candidate solutions. By maintaining a population of candidate configurations and applying selection pressure toward better-performing configurations, evolutionary search can effectively navigate toward the Pareto frontier. In our case, we use a simple mutation-based algorithm that creates new solutions by modifying existing ones.

\paragraph{Initialisation.}
The evolutionary search starts with an initial pool $\mathcal{P}_0$ of $n_\mathrm{init}$ configurations. These configurations are generated using the same random sampling approach as in the random search strategy, ensuring that the initial pool is diverse and covers a broad area of the search space. Each configuration in the initial pool is evaluated with $K$ Monte Carlo replications. 

\paragraph{Mutation operator.}
The mutation operator receives a parent configuration
$\mathbf{c} = (N, \mathbf{A}_\mathrm{dev}, \mathbf{A}_\mathrm{qa}, R, F_\mathrm{freeze})$
and produces a child by perturbing exactly one randomly chosen parameter.
$R$ is never mutated, i.e., the release cadence is only sampled when generating the initial population.
The parameter to perturb is selected uniformly at random from four choices:
\begin{itemize}
  \item \emph{Mutate $N$:} replace the current value with an adjacent value in the
        discrete set $\mathcal{N}$ (the next smaller or larger element).
  \item \emph{Mutate $F_\mathrm{freeze}$:} apply $\pm 1$ while ensuring that $F_\mathrm{freeze}$ stays in $[0, R-1]$.
  \item \emph{Mutate $\mathbf{A}_\mathrm{dev}$:} apply one elementary operation drawn uniformly from:
        \begin{itemize}
          \item \emph{Add}: increment one randomly chosen supervised role by~1, provided it
                stays at or below its saturation bound $u_k$.
          \item \emph{Remove}: decrement one randomly chosen non-empty supervised role by~1.
          \item \emph{Move}: select a random non-empty supervised donor role and transfer one agent to a randomly chosen
                supervised recipient role that is still below its saturation bound $u_k$.
          \item \emph{Adjust service}: apply $\pm 1$ to one of the two background detection
                services, floored at zero. This operation is separate from the three above because
                these roles require no supervision and are not part of the pool that the three
                operations above redistribute, and it has no upper bound.
        \end{itemize}
  \item \emph{Mutate $\mathbf{A}_\mathrm{qa}$:} works the same as for $\mathbf{A}_\mathrm{dev}$, except that the implementation and architecture roles ($k = 1, 2$) remain fixed at zero.
\end{itemize}
If a mutation attempt produces an invalid configuration or leaves the parent unchanged
(e.g.\ because the chosen role is already at its
saturation bound, or because a randomly chosen operation
is a structural no-op), the attempt is discarded and a new mutation type is drawn.
Up to ten attempts are made; if none yields a distinct valid child, the parent is
returned unchanged.

\paragraph{Generation loop.} The generation loop iteratively produces new configurations by mutating selected parents from the current pool of configurations. The loop is repeated for $g=1,\ldots,G$ generations. In each generation, the following steps are performed:
\begin{enumerate}
  \item Compute the current CI-aware Pareto frontier $\mathcal{F}_{g-1}$ over the previously generated population $\mathcal{P}_{g-1}$.
  \item Sample $n_\mathrm{off}$ parent configurations. 80\% of the parents are drawn uniformly from $\mathcal{F}_{g-1}$ to search for better solutions along the Pareto front. 20\% of the parents are drawn uniformly from $\mathcal{P}_{g-1} \setminus \mathcal{F}_{g-1}$ to enable exploration of the search space in other regions.
  \item Apply the mutation operator to each parent, creating the child population $\mathcal{P}_{g,child}$.
  \item Create the new population $\mathcal{P}_g$ as the union of the child population and the current population: $\mathcal{P}_g = \mathcal{P}_{g-1} \cup \mathcal{P}_{g,child}$.
\end{enumerate}

The mixture of drawing most mutations from the Pareto frontier and some from the rest of the population is designed to balance exploitation and exploration: the former focuses the search on improving the best-known configurations, while the latter allows for discovering new regions of the search space that may contain better configurations.

\paragraph{Final frontier.}
At the conclusion of the generation loop, the CI-aware Pareto frontier is computed over $\mathcal{P}_G$, which contains all feasible, simulated configurations evaluated across all generations.

\subsection{Scenarios}
\label{sec:setup:scenarios}

There are five orthogonal aspects that influence our simulation, each governed by a distinct group of scenario parameters that we define in the following subsections: human developers, project dynamics, debt dynamics, agent costs and throughput, and bug impact. Each group contains multiple parameters that govern different facets of that aspect. For each of these aspects, we define three levels of parameters, corresponding to a low, medium, and high setting. For example, agent capabilities can be lower or higher, varying the correctness and costs of agentic actions. Orthogonally, developers may be junior, mid-level developers, or seniors resulting in different capabilities and salaries. 
Since the groups are orthogonal, we can freely combine all five groups into a diverse set of scenarios. 

\subsubsection{Human developer parameters}

The scenario parameters for human developers are summarized in Table~\ref{tab:scenario:human}.
We assume that a full-time developer works a 40-hour week, i.e., $H_\mathrm{capacity}$ is stated per FTE and a staffing level of $N=0.25$ corresponds to a ten-hour week. We assume that the communication overhead is one hour per team member. We further assume that humans spend equal time bug fixing and implementing features within the time not required for other tasks. The salaries are estimated based on average salaries reported by Indeed~\citep{indeed2026salaries}. We round low, average and high salaries to the next \$50k, to account for the employer overhead costs.

While there is no data yet on how much time developers require to monitor agents, early results indicate that there is a fairly low interruption frequency~\citep{baumann2026swechat}, so we set the monitoring overhead at a modest 2.5 hours per week, i.e., 30 minutes per day. The work capacity $H_\mathrm{capacity}$, the communication overhead $c_\mathrm{comm}$, the monitoring overhead $H_\mathrm{mon,overhead}$, and the bug-fixing share $f_\mathrm{fix}$ are independent of developer skill and are therefore the same across all three tiers. There are also no estimates yet how much time developers require to resolve an agent escalation. It is reasonable to assume that these are non-trivial problems that require developers to get involved with the code base, so we assume that the time required is similar to that required to implement a feature (estimate see below).

We use the review of architectural decision records (ADRs) to ground the architecture-review time within our model. Amazon estimates 10--15 minutes to read the document~\citep{amazonArchitecturalDecision}. The process is assumed to be iterative and done by multiple developers. Assuming that updating the ADR based on comments requires 45 minutes, one iteration would require 1 hour. With 4 iterations, this would require a total of 4 hours, which we use for the medium tier. We assume that less capable developers require twice as long and highly capable developers are twice as fast, resulting in 8 hours for the low tier, and 2 hours for the high tier.

To have a comparable baseline for human effort, we assume the time required to solve SWE-bench Verified coding tasks, which are designed to be representative of real-world coding tasks by basing them on issues reported in open-source repositories~\citep{openai2026swebenchverified,jimenez2024swe}. We use METR's estimate for the human baseline of the time required to solve substantial issues within the 1--4 hour time bucket of the benchmark, which estimates the time at 2 hours~\citep{kwa2026measuringaiabilitycomplete}. Since this seems reasonable, we use this for the medium tier. We use the pattern that less capable developers require twice as long as the medium tier and highly capable developers are twice as fast, resulting in 4 hours for the low tier, and 1 hour for the high tier. Since METR found that the $<15$ minute time bucket underestimates the time required to solve tasks, we instead use the 15 to 60 minute time bucket to estimate the time required to fix bugs in a similar manner, i.e., 30 minutes for the medium tier, 60 minutes for the low tier, and 15 minutes for the high tier.

As per our modeling assumptions, the rate that humans introduce bugs is based on the agentic bug introduction rate using a multiplicative factor, such that a value of 1 means equal behavior and values less than one mean that humans introduce fewer bugs than agents. \cite{coderabbit2025aicode} reports that AI introduces issues at 1.7 times the rate of humans. Since this number is one year old at the time of writing, we use it as the baseline for the high tier, i.e., the most capable humans, assuming progress by later models that improved performance in SWE-bench Verified and other benchmarks. Since junior developers are frequently compared to AI agents~\cite{kumar2025ai}, we use a factor of 1 for the low tier. We use the mid-point, i.e., 1.35 for the medium tier. This results in a bug introduction rate factors of $\frac{1}{1.7}=0.58$ for the high tier, $\frac{1}{1.35}=0.74$ for the medium tier, and 1 for the low tier.

\subsubsection{Project dynamics parameters}

To understand the project dynamics, we first collected data from all projects with at least 100 issues and at least 10 stars using SEART's GitHub Search tool~\citep{dabic2021data}. We then filtered these projects such that they have an average activity of at least 10 commits per week, i.e., consistently active commit activity during their lifetime. From the resulting projects, we considered the 1{,}000 projects with the most stars, i.e., that are popular and actively engaged by the community. We then compute the number of issues per week and use the 5th percentile for the low tier, the 50th percentile for the medium tier, and the 95th percentile for the high tier for the number of issues per week. We note that these estimates are only valid for open source projects and may not be representative of closed-source projects. The resulting parameters are summarized in Table~\ref{tab:scenario:project}.

To understand how often issues affect architecture, we use data from \cite{shahbazian2018toward}, who used automated methods to determine whether the change triggered by an issue caused architectural changes. Depending on the method used, the proportion ranged from 13\% of issues to 26\% of issues. Since the automated approach possibly overestimates the proportion by counting purely structural changes, we use the lower bound of 13\%. We derive the data for the distribution of the severity of bugs from data collected by \cite{ohira2015highimpact}. They distinguish between critical, blocker, and major issues (which we map to major bugs), and minor and trivial issues (which we map to minor bugs). Orthogonally, they determine which of these bugs are security related, which we use to infer the ratio of security bugs. We exclude one of the collected projects (Ambari) for the estimation of the ratio of major bugs, since it did not mark issues as minor.
These numbers are independent of the number of issues per week and therefore the same across all three tiers.

\subsubsection{Debt dynamics parameters}

The debt dynamics parameters are summarized in Table~\ref{tab:scenario:debt}. There is a limited amount of literature on the impact of documentation and the studies are typically conducted with small sets of developers, limiting their ability to find significant effects. \cite{dzidek2008uml} found an increase in maintenance time of 40\% when no UML documentation was made available based on a group of 20 developers. In a recent eye tracking experiment using 12 (mostly junior) developers, \cite{abdelsalam2026comments} found an increase in program comprehension time of up to 34\% based on code comments, but this effect depended on the complexity of the code and comprehension time was even reduced for simpler code snippets. Based on these studies, we set the low tier to 0\% (no effect due to lack of significance of results), the medium tier to 34\% (the maximum effect found by \cite{abdelsalam2026comments}), and the high tier to 40\% (the effect found by \cite{dzidek2008uml}).

We estimate the addition of technical debt based on data from \cite{he2026cursordebt}, who found that AI-assisted coding increases code complexity and static analysis warnings. We note that this is particular to AI-assisted development as the technical debt otherwise seems to be decreasing over time \cite{trautsch2020longitudinal}. Since the average treatment effect found that AI-assisted development leads to 28\% more lines, but 30\% more static analysis warnings, we assume that the debt increases by at least 2\% for every feature added. Since \cite{he2026cursordebt} also found that the complexity increases by 41\% due to the use of AI, we assume that the upper bound for the debt-increase is 13\% per feature added. We therefore set the low tier to 2\%, the medium tier to 6\% and the high tier to 13\% per feature added. Since \cite{trautsch2023automated} found that there is no detectable difference between the static analysis warnings added by bug fixing commits and other commits, we use the same values for the debt increase due to bug fixing. 
% We note that at the refactoring throughput $r_\mathrm{refactor}$ of Table~\ref{tab:scenario:agents} a single Refactoring Agent removes more debt per sprint than any of our scenarios accumulates, so $a_{\cdot,4} \geq 1$ holds $D_\mathrm{tech}$ at zero and $\delta_\mathrm{impl}$ and $\delta_\mathrm{fix}$ only bind while the role is unstaffed.

We set the values for the debt amplifier floor $\delta_\mathrm{min}$, i.e., the fraction of the nominal throughput that is retained at maximal debt, based on a developer survey from \cite{besker2018technical}. They found that developers spend on average 23\% of their time dealing with technical debt with a standard deviation of 17\%. We interpret this share $s$ of lost time as the slow-down at maximal debt and hence set $\delta_\mathrm{min} = 1 - s$. We therefore set the low value at $0.94$ (i.e., a slow-down of 6\%, one standard deviation below the average), the medium value at $0.77$ (a slow-down of 23\%, the average), and the high value at $0.60$ (i.e., a slow-down of 40\%, one standard deviation above the average). The work \cite{martini2027interest} found that technical debt can be contagious, which supports a non-linear effect of the technical debt. Since there is no data on how strong this non-linearity is, we assume a slightly super-linear effect with $\delta_\mathrm{exp} = 1.5$ across all scenarios.

\subsubsection{Agent costs and throughput parameters}
\label{sec:scenario:agentcosts}

The agent cost parameters are summarized in Table~\ref{tab:scenario:agents}. While there is no direct scientific evidence for the exact costs per feature implementation, we assume that implementing a feature requires 100 tool calls, 2M cumulative input tokens, and 40K output tokens~\citep{morph2026aicodingcosts}. For bug fixes, we assume 25 tool calls, 400K cumulative input tokens, and 10K output tokens~\citep{morph2026aicodingcosts}. The costs for the other activities are grounded on these two costs:
\begin{itemize}
  \item Code review is assumed to be comparable to bug fixing, since similar analysis needs to be performed to understand the code and its implications. Security audits are more thorough and assumed to be ten times more expensive than normal code review.
  \item Architecture and design changes possibly require an analysis of the whole code base to understand the implications. Therefore, we assume that these carry high costs, comparable to the cost of implementing five features.
  \item Refactoring is assumed to be comparable to implementing a feature, since it requires a similar amount of analysis and code changes.
  \item Writing tests and documentation are assumed to be comparable to bug fixing, since it requires a similar analysis of a local context.
\end{itemize}
We further ground the pricing based on the API pricing of Claude Sonnet~5, Opus~5, and Fable~5 for low, medium, and high, respectively.

We model the throughput using the same assumptions on the relation between the throughput of the models as for the cost parameters, but base these estimations on the latency of the models, i.e., the time to solve a task. Since a concrete latency is hard to define as this depends not only on model size, but also on the current load of cloud providers, we do not estimate this on single latency values that are reported. As for the other tasks, we ground this in SWE-bench, where the reference solutions require 107 lines of code on average~\citep{scaleSWEBenchPublic}. Based on data from \cite{baumann2026swechat}, autonomous coding required 12.6 minutes on average per 100 commit lines. Assuming that agents only run during work hours, this would result in 178 features per sprint, resulting in the throughput rates reported in Table~\ref{tab:scenario:agents}.

We estimate the agentic bug introduction rate based on the SWE-bench Verified benchmark score, assuming that each failure in the benchmark results in a bug in the code base. We collect the data for Claude Sonnet~5, Opus~5, and Fable~5 analogously to the cost estimations. The values are taken from the vals.ai leaderboard~\citep{valsai2026swebench}, i.e., we do not use Anthropic's estimates but those of independent benchmark executions. While we are aware that these results likely overestimate the actual benchmark performance~\citep{liang2026swe}, we nevertheless use this as an (optimistic) estimate for the capabilities of the agents.

We use CyberBench~\cite{liu2024cyberbench} to estimate the security bug detection rate. While the benchmark is not a perfect fit, since it also includes the correction of the bug, it still gives us a good baseline for the detection rate. For other benchmarks, like SEC-Bench Pro, we could not find data for recent models that are not self-reported by the model providers. Due to the model guardrails, we also cannot use the performance of the Claude~5 models here and instead use the GPT-5.6 models (Luna, Sol) and the scores reported by vals.ai~\citep{valsai2026swebench} for the medium and high tiers. Data for GPT-5.6 Terra is also not available; we therefore estimate that the difference between Terra and Luna is the same as between Luna and Sol. We estimate the capability to generate tests based on data from \cite{huang2025benchmarking}, who developed a benchmark with unit tests for functions that were not part of the training. They found that test generation capability strongly correlates with coding ability, but models scored lower on the test generation benchmark, with differences of at least 0.2. Since no similar benchmark exists for the latest models, we assume that the trend holds and use the same difference here, i.e., the SWE-bench scores reduced by 0.2.

We use SWE-Review~\citep{wang2026swe} to estimate how good language models are at code review. Within this benchmark, Claude Opus 4.6 was able to correctly judge pull requests for between 75\% and 89\% of the cases. We use these as low and high tier respectively and use the mid-point 0.82 for the medium tier. To estimate the ceiling of what testing can achieve, we use research from \cite{SCHWARTZ2018106} as foundation: they found that even for highly covered projects, 46\% of mutants could not be detected by the test suite, giving a ceiling of 0.54, which we use as the medium estimate. We assume that less capable agents are worse at testing, while more capable agents are better, resulting in a low tier of 48\% and a high tier of 60\%.

Finally, we estimate the escalation rate based on telemetry data from \cite{baumann2026swechat}: in their study, the agents escalated between 1\% and 3\% of the time, which we use as the high and low tier respectively, since less capable agents are expected to escalate more often. We use the mid-point 0.02 for the medium tier.

\subsubsection{Bug impact parameters}

The severity weights $\omega_\mathrm{min}$, $\omega_\mathrm{maj}$, and $\omega_\mathrm{sec}$ reflect how much a minor, major, or security bug that escapes to production actually costs once it affects real users. We ground these weights in real-world estimates of such costs, distinguishing three system contexts that match our low, medium, and high tiers: a simple web application (e.g., a small SaaS product), an enterprise system with a large user base and a formal incident-response process, and a safety-critical system such as a medical device. Since $\omega_\mathrm{min}$, $\omega_\mathrm{maj}$, and $\omega_\mathrm{sec}$ are only used as relative weights within the quality objective, we fix $\omega_\mathrm{min}=1$ for every tier and derive $\omega_\mathrm{maj}$ and $\omega_\mathrm{sec}$ as the ratio between the estimated real-world cost of a major, respectively security, incident and the cost of a minor bug for that tier.

We estimate the cost of a minor bug as the direct engineering cost of a single feature for a human developer, i.e., two hours of time. We compute this using the fully-loaded hourly rate implied by $c_\mathrm{salary}$ in Table~\ref{tab:scenario:human} (assuming a 2080-hour work year), giving \$100, \$150, and \$250 for the low, medium, and high tier, respectively. Notably, this also means that such bugs have no direct external incident costs, i.e., because they are just nuisance bugs that do not affect functionality.

For major bugs, i.e., defects that break or degrade a feature in production for a non-trivial period, we ground our estimate in reported downtime costs. For the low tier, ITIC's 2024 downtime survey reports that small and mid-sized businesses commonly estimate the cost of an hour of downtime at around \$25{,}000~\citep{itic2026downtime}. For the medium tier, industry estimates put the cost of an hour of downtime for a critical enterprise application at over \$300{,}000~\citep{cloudqa2026bugcost}, which is consistent with ITIC's finding that 97\% of large enterprises report hourly downtime costs exceeding \$100{,}000~\citep{itic2026downtime}. In both cases, we use these numbers directly, i.e., we assume a prompt response mitigating the issue within one hour. For the high tier, we ground the estimate in the medical device industry: McKinsey estimates that significant quality events (recalls, FDA enforcement actions, and litigation) cost the global medical device industry \$7--8.5 billion annually~\citep{mckinsey2026medtech}, and software defects caused an estimated 8.2\% of the 1{,}059 US medical device recall events recorded in 2024, i.e., about 87 events~\citep{meddeviceguide2026recalls}. Distributing the midpoint of McKinsey's estimate (\$7.75 billion) proportionally over these 87 software-related recalls gives an average cost of about \$7 million per event, which we use as our high-tier estimate.

For security bugs, i.e., defects that are exploited after reaching production, we ground our estimate in reported breach and incident costs from CISA's systematic review and cross-validation of cyber incident cost data~\citep{cisa2020cybercost}, which pools several commercial claims datasets and recommends using the median rather than the mean per-incident cost, since the underlying loss distributions are heavily right-skewed. For the low tier, we use the median total incident cost of \$48{,}000 reported for small and mid-sized businesses in NetDiligence's 2019 Cyber Claims Study (2{,}003 claims, revenue-based segmentation), as tabulated in the CISA review~\citep{cisa2020cybercost}; we use this as representative of a small web application operator. For the medium tier, we use the median total incident cost of \$1.0 million reported for large entities in the same NetDiligence (2019) dataset (78 claims)~\citep{cisa2020cybercost}, which reflects the larger, more heavily regulated organizations that make up a typical enterprise. For the high tier, we use the cost of the 2017 WannaCry ransomware attack on the UK's National Health Service, which exploited a security vulnerability to disrupt hospital operations and cancel 19{,}000 patient appointments at an estimated cost of \pounds92 million (about \$120 million), as reported by the UK Department of Health and Social Care~\citep{nhe2018wannacry}, since the CISA review does not contain a comparable estimate for safety-critical or healthcare-specific systems and this figure directly ties a real security exploit to disruption of safety-critical services rather than to data loss alone.

Dividing the major- and security-bug cost estimates by the corresponding minor-bug cost gives the severity weight ratios reported in Table~\ref{tab:scenario:bugimpact}. The resulting weights increase substantially from the low to the high tier, reflecting that the same class of defect is far more costly to tolerate in systems with larger user bases, stricter regulatory obligations, or direct safety implications.

\subsection{Experiment Configurations}
\label{sec:setup:sweep}

\paragraph{Scenario grid.}
Since we have five orthogonal aspects, each with three levels, we have a total of $3^5 = 243$ scenarios. We solve each of these problems twice, once with uniform random search and once with evolutionary search (Section~\ref{sec:model:search}), which yields 486 searches in total.
All scenarios share the same initial state, simulation horizon, and Monte Carlo protocol, so that any difference between two frontiers is attributable to the scenario parameters and not to the experimental setup. The constants are summarised in the upper part of Table~\ref{tab:setup:experiment}. We simulate a green-field project, i.e., every component of the initial state $S(0)$ is empty, meaning no feature backlog, no bugs in any of the twelve bug queues, no technical debt, empty human capacity queues, no tests, and no developer documentation. We use short 1-week sprints and two-year projects. The length of the time horizon is chosen to give debt time to accumulate to be able to observe negative effects. We use $K = 100$ replications per configuration. 

The lower part of Table~\ref{tab:setup:experiment} gives the search range in the sense of Section~\ref{sec:model:search}. The staffing levels range in quarter-FTE steps from a single developer investing one day per week up to a small five-person team. Larger teams do not make sense, since this is not supported by the feature arrival speed. The range extends below one FTE because the opposite problem arises at the other end of the project spectrum: at the low project tier, features arrive at $r_\mathrm{arrival} = 3$ per sprint, which a single full-time developer supported by agents exceeds by a wide margin, so that the interesting configurations for such projects are part-time ones.

The human-capacity condition of Eq.~\eqref{eq:feas_monitoring} caps how many supervised agents a staffing level can carry: with $H_\mathrm{mon,overhead} = 2.5$\,h and the documentation reduction factors $\Gamma_\mathrm{doc} \in \{0, 0.34, 0.40\}$ of Table~\ref{tab:scenario:debt}, monitoring alone exhausts a full-time developer's net capacity at roughly 16, 24, and 27 supervised agents \emph{per FTE}, respectively.

The release cadences $\mathcal{R} = \{1, 2, 4, 13\}$ cover continuous delivery (a release after every sprint), a biweekly, a monthly, and a quarterly release train, and the feature-freeze lengths $\mathcal{F}_\mathrm{freeze} = \{0, 1, 2\}$ cover no freeze, a one-week, and a two-week freeze. Both are combined subject to $F_\mathrm{freeze} \leq R - 1$ as described in Section~\ref{sec:model:search}, so $R = 1$ admits only $F_\mathrm{freeze} = 0$. 

Both search strategies receive the same budget of $E = 10\,000$ candidate evaluations per scenario, so that the comparison between them measures search efficiency and not effort. For random search this means $n_\mathrm{rand} = 10\,000$ candidates. For evolutionary search we spend 10\% of the budget on the initial pool and 90\% on the generation loop, i.e., $n_\mathrm{init} = 1\,000$, $G = 90$ generations, and $n_\mathrm{off} = 100$ offspring per generation.

Candidates that violate the human-capacity condition are recorded and counted against the budget, but not simulated, and the same accounting applies to both strategies. In addition, the mutation operator may fail to produce a new, distinct, feasible child within its attempt limit, and duplicate children are not re-evaluated, so the number of configurations that an evolutionary run actually simulates can fall slightly below the nominal budget. We therefore report the realised number of simulated configurations.
